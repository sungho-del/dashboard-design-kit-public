## 1. 전달 범위

**이 폴더는 이식 검토를 위한 시각·상호작용 _제안_ 기준본이다. 제품 코드가 아니다.**

이 저장소의 Next 앱은 이미 셀러 API 에 연결돼 동작한다. 이 폴더는 그 화면들에 Clay 디자인 시스템을 입혔을 때
**어떻게 보이고 어떻게 반응하는지**를 보여 주는 별도 프로젝트다(본사 어드민 `babycube-admin-hq` 의 `publishing/` 과 같은 방식·같은 톤).
폴더를 넣는다고 제품 화면이 바뀌지 않는다.

⚠️ **이 저장소의 UI 기준선(`reference/`)과 정책 규범 서열을 대체하지 않는다.** 원본 기획과 다르게 보이는 곳은
`docs/OPEN-DECISIONS.md` 판정을 거친 뒤에 적용하고, 적용하더라도 `publishing/` 밖에서 한다.

## 2. 실행

```bash
cd publishing
npm ci
npm run dev          # http://localhost:5173 — GNB 맨 아래 「화면 목록」(/screens)에서 전 화면으로 간다
npm test -- --run
npm run build        # dist/
```

검증 환경: Node 24.18 · npm. 루트 Next 앱과 의존성을 공유하지 않는 독립 프로젝트다.

### 알아둘 규칙 (어기면 조용히 깨진다)

- **색은 semantic 토큰만** (`bg-surface`, `text-text-sub` …). hex·primitive 금지. 주 버튼은 near-black(`action-primary`)
- **타이포는 프리셋만** (`heading-2xlarge-bold`, `body-medium`, `metric-small` …). `text-sm` 류 금지
- **경계선·포커스는 `outline` + 음수 offset** — `border` 를 쓰면 레이아웃이 밀린다
- `src/lib/cn.ts` 는 **클래스를 병합하지 않는다** — 같은 속성 클래스를 두 곳에서 내보내면 둘 다 남는다
- Tailwind 는 `src/styles/tokens.css` 의 `@source` 로 스캔 범위를 **명시**한다. 새 소스 폴더는 거기 등록
- 금액·상태 계산은 화면이 하지 않는다 — `orderUnit.data.ts`(처리단위 · 원본 식) · `claim.data.ts` · `settle.data.ts` · `ProductsPage.data.ts`(`saleStatOf`)가 한 곳에서 낸다
- GNB 는 `pages/seller/SellerGnb.tsx` 하나로 그린다(직영 미리보기가 여기서 메뉴를 거른다)
- **목록 표는 모든 `<col>` 에 폭을 준다** — `Table` 이 `w-max` 라 폭 없는 열은 내용만큼 늘어난다. 표 안 말줄임은 `truncate` 가 아니라 `line-clamp-1`
- **글머리표는 도형**(`pages/babycube/BulletList.tsx`) — 「·」 글자·`list-disc` 를 쓰지 않는다

## 4. 실제 화면에 반영하기로 판정되면

`docs/INTEGRATION.md` 에 화면별로 **이 저장소의 기존 데이터 모듈(`src/data/*`)** 과의 대응을 적었다. 요지:

- 데이터 계약은 **기존 Next 앱의 것이 정본**이다. 퍼블 `.data.ts` 타입에 서버를 맞추지 않는다
- 퍼블은 시드 배열을 **브라우저에서** 거르고 센다. 기존 앱은 `makeListApi`(`src/data/admin-list.ts`)로 **서버에서** 받는다 — 퍼블의 필터 상태를 `ListQuery` 로 옮기면 된다
- 처리단위 식별자는 `{주문번호}-{순번}`(예 `20260624225758-1`) — 서버의 처리단위 키와 같은지 먼저 확인할 것

## 7. 기획 확인 필요 · 알려진 이슈

원본 기획끼리 맞지 않거나 규칙이 없는 곳은 **원본대로 두고** 각 화면 `.data.ts` 머리 주석에 「기획 확인 필요」로 적었다. 큰 것만:

| 영역      | 항목                                                                                                                                                        |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 주문 전반 | 셀러 목록에 본사 자체 처리단위 6건이 섞인다 · 결제에 없는 처리단위 1건 · 표 결제금액(계산) ≠ 저장 금액                                                      |
| 렌트      | 목록 「옵션 총액」(정액 1회) vs 명세(일가 × 렌트일) · 조기 반납 판정은 글자 근사                                                                            |
| 정산      | 확정 거래액 = **정가**(본사 퍼블은 할인 후 — 두 앱 기준이 다르다) · 「지급일 · D-3」 기준일과 불일치 · 지난 회차 고정값 · 세금계산서 공급가액 = 차감 × 0.72 |
| 보증금    | 요약 타일은 보증금 있는 렌트 전체 · 목록은 검수 이후 18건                                                                                                   |
| 상품      | 기간 기준 「판매시작일·판매종료일」 값 없음 · 「기본 렌트일」 필수 표시인데 검사 없음 · 옵션 재고 전부 0                                                    |

### 이 폴더를 갱신하는 규칙

1. `publishing/` 은 **읽기 전용 기준본**이다. 여기서 직접 고치지 않는다 — 고칠 것이 있으면 퍼블 담당에게 알린다
2. 갱신은 디자인 키트 저장소에서 **다시 추출**해 PR 로 올린다(`npm run export:publishing -- <폴더> --app seller`). 맨 위 「추출 기준」 커밋이 버전이다
3. 갱신 전, 직전 전달 이후 이 폴더가 바뀌었는지 확인한다: `git log <직전 전달 커밋>.. -- publishing/` · `git status --short --untracked-files=all -- publishing/`
