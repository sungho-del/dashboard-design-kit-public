# DESIGN — 대시보드 레이어

> **이 문서의 자리**: `DESIGN.md` **§0**(앱 셸 껍데기)과 **§28**(차트 그림 안쪽) 사이의 공백을 메운다.
> §0 은 "화면의 테두리"를, §28 은 "차트 안쪽"을 정하지만, **그 사이에 있는 것** —
> 지표 타일 · 타일 그리드 · 수치 타이포 · 증감 표현 · 데이터 상태 — 은 어느 쪽도 다루지 않았다.

## §D1. 대시보드가 범용 DS 에 더하는 것

범용 디자인 시스템은 **컴포넌트**를 준다. 대시보드는 그 위에 **레이어**를 요구한다.
"Card 를 하나 더 만드는 일"이 아니라, Card 가 모르는 것들을 정하는 일이다.

| #      | 레이어           | 범용 DS 가 모르는 것                                                  | 이 문서       |
| ------ | ---------------- | --------------------------------------------------------------------- | ------------- |
| **L1** | 지표 표현        | `Card` 는 컨테이너일 뿐 **수치의 의미 구조**를 모른다                 | §D3 · §D5     |
| **L2** | 대시보드 그리드  | 타일은 **면적으로 우선순위**를 말한다 — 폼 그리드와 규칙이 다르다     | §D2           |
| **L3** | 밀도             | 어드민은 같은 화면을 하루 8시간 본다                                  | §D10 (설계만) |
| **L4** | 데이터 상태      | 범용 DS 는 "폼 검증 에러"만 안다. 대시보드는 **타일 단위로 실패**한다 | §D8           |
| **L5** | 데이터 시각화 색 | 시맨틱 색(success·critical)과 **다른 레이어**다                       | §D7           |
| **L6** | 수치 표현 규약   | Typography 는 "크기"만 정하고 **"숫자 렌더링"은 안 정한다**           | §D6           |
| **L7** | 드릴다운         | 대시보드는 종착지가 아니라 **관문**이다                               | §D3-5         |
| **L8** | 차트 접근성      | **SVG 는 스크린리더에 내용이 전달되지 않는다**                        | §D9           |

> `[외부]` IBM Carbon 은 카드 패턴을 **아예 코어에 두지 않는다**("Carbon does not have a card
> pattern, but we link out to several card patterns within our pattern asset library").
> 대시보드 레이어를 코어 밖에 두는 것도 정석적 선택이다 — 이 문서를 `DESIGN.md` 안이 아니라
> **별도 파일**로 둔 이유가 그것이다.

## §D2. 대시보드 그리드

### D2-1. 콘텐츠 실폭 `[실측]`

앱 셸이 이미 폭을 정해 놓았다. GNB 224 + gutter 40 × 2 = **304px 가 항상 빠진다.**

| 뷰포트   | 콘텐츠 실폭 | 4열 타일 폭 | 3열 타일 폭 |
| -------- | ----------- | ----------- | ----------- |
| 1280     | 976         | **226**     | 309         |
| 1440     | 1136        | **266**     | 363         |
| **1600** | **1296**    | **306**     | 416         |
| 1920     | 1616        | **386**     | 523         |
| 2560     | 2256        | **546** ⚠️  | 736 ⚠️      |

(4열 = `(실폭 − gap 24 × 3) ÷ 4` · 3열 = `(실폭 − gap 24 × 2) ÷ 3`)

### D2-2. 규격

| 항목           | 값                                               | 근거                                                                       |
| -------------- | ------------------------------------------------ | -------------------------------------------------------------------------- |
| 거터           | **24** (`gap-6`)                                 | `[판단]` `AppShell` 이 이미 카드 간격 24. Clay 실측 "카드↔카드 24" 와 같다 |
| 기본 열 수     | **4열**                                          | `[판단]` 1280 에서 226px — 타일 최소폭을 넘기는 최대 열 수                 |
| 타일 최소폭    | **220**                                          | `[판단]` 1280 4열(226)이 지나가고, 그 아래는 3열로 접힌다                  |
| 반응형         | `grid-cols-[repeat(auto-fit,minmax(220px,1fr))]` | 열 수를 폭이 정한다 — 브레이크포인트를 손으로 관리하지 않는다              |
| 타일 최소 높이 | **2:1 종횡비 이상**                              | `[외부]` Carbon Tile                                                       |
| 차트 카드 높이 | **240** (`ChartFrame` 기본)                      | `DESIGN.md` §28-2                                                          |

> ⚠️ **2560px 에서 4열 타일이 546px 로 벌어진다.** 라벨과 수치 사이가 비어 한 덩어리로 안 읽힌다.
> `auto-fit` + `minmax` 를 쓰면 폭이 남을 때 **열이 늘어나** 타일이 과하게 넓어지지 않는다.
> `[외부]` 참고로 1600px 에서의 콘텐츠 폭 1296 은 Atlassian 대시보드 `fixed-wide` 최대폭과 같다.

### D2-3. 섞지 말 것

> `[외부]` Polaris: _"high-density 컴포넌트와 low-density 컴포넌트를 같은 카드에 섞지 말 것."_

한 카드 안에 **표(고밀도)와 지표 타일(저밀도)을 함께 넣지 않는다.** 시선의 보폭이 달라
어느 쪽도 제대로 읽히지 않는다. 나눌 때는 카드를 나눈다.

### D2-4. 지금 어긋나 있는 것 `[실측]`

같은 성격의 타일 행에 `gap-3`(12) 5회 · `gap-4`(16) 3회 · `gap-6`(24) 9회가 섞여 있다.
**새로 만드는 화면은 24 로 통일한다.** 기존 화면은 이 문서의 범위 밖이다(일괄 교정 시 별도 작업).

## §D3. StatTile — 대시보드의 기본 단위

> 구현: `src/components/ui/StatTile/`

### D3-1. 두 방언, 하나의 컴포넌트

이 저장소에는 지표 타일이 **두 형태**로 존재했고 **둘 다 쓰임이 있다.** 하나를 버리면
그 화면들을 전부 고쳐야 한다. 그러므로 **variant 로 흡수한다.**

| variant     | 생김새                                  | 쓰이는 곳                                 | 채택       |
| ----------- | --------------------------------------- | ----------------------------------------- | ---------- |
| **`plain`** | 회색 면 · 값/단위 분리 · 클릭 가능      | 필터 대시 · 지표 그룹 카드 안 · 상태 흐름 | **12화면** |
| **`card`**  | 흰 카드 · 아이콘칩 · 증감 Tag · caption | 통계형 상단 KPI 행 · 요약 밴드            | **5화면**  |

> ⚠️ **`card` 안에도 두 배치가 있었다** — 값이 별도 행인 A형(대시보드 2곳)과
> 라벨+값을 묶어 아이콘과 나란히 두는 B형(목록 요약 2곳). 승격하며 **A형으로 통일**했다.
> 값이 한 단 커지면서(20~24 → 30) 아이콘 옆에 눌러 담기 어려워졌고, 무엇보다
> 한 컴포넌트가 배치를 둘로 유지하면 승격의 목적이 사라진다.
>
> **`plain` 은 "항목"이고 `card` 는 "그 자체로 카드"다.** `plain` 은 흰 카드(`Card`) 안에
> 들어가는 부품이라 배경이 `surface-sub` 여야 층이 생긴다. `card` 는 혼자 서므로 흰 면이다.
> 이 구분을 지키지 않으면 **회색 면 위에 회색 면**이 얹혀 경계가 사라진다.

### D3-2. Anatomy

```
variant="plain"                        variant="card"
┌──────────────────────────┐           ┌──────────────────────────┐
│ ① 라벨                   │           │ ① 라벨          ⑥ 아이콘칩│
│                          │           │ ② 1,284                  │
│           ② 1,284 ③ 건 ⑤│           │ ④ ▲12%  ⑦ 지난주 대비    │
└──────────────────────────┘           └──────────────────────────┘
```

| #   | 요소      | 필수 | 규격                                                              |
| --- | --------- | ---- | ----------------------------------------------------------------- |
| ①   | 라벨      | ✅   | `body-medium` · `text-text-sub` · 문장부호 없음                   |
| ②   | 값        | ✅   | `metric-*` (§D6-1) · `text-text` · **비례폭**                     |
| ③   | 단위      | —    | `body-medium` · `text-text-sub` · **값과 다른 요소** (§D3-3)      |
| ④   | 증감      | —    | `Tag` + 방향 아이콘 · 색은 `chart-delta-*` (§D6-5)                |
| ⑤   | 이동 표식 | —    | `ArrowUpRight` 16 · **갈 곳이 있을 때만** (§D3-5)                 |
| ⑥   | 아이콘칩  | —    | `size-10 rounded-medium bg-surface-sub text-icon-sub` · 아이콘 20 |
| ⑦   | 캡션      | —    | `body-small` · `text-text-minimal` · **비교 기준을 밝힌다**       |

### D3-3. 값과 단위는 다른 요소다

```
❌  <strong>1,284건</strong>
✅  <strong className="metric-small">1,284</strong>
    <span className="body-medium text-text-sub">건</span>
```

`items-baseline` 으로 묶으면 크기가 달라도 **글자 밑선이 맞는다.** 단위를 값에 붙여 쓰면
단위까지 36px 로 커져 수치의 자릿수가 몇인지 한눈에 안 들어온다.

### D3-4. Spec

값은 **variant·compact 조합마다 다르다.** 한 줄로 뭉뚱그리면 구현과 어긋난다.

| Element   | Property   | `plain` 기본         | `plain` + `compact` | `card`                             |
| --------- | ---------- | -------------------- | ------------------- | ---------------------------------- |
| 타일      | radius     | 8                    | 8                   | 8                                  |
| 타일      | background | `surface-sub`        | `surface-sub`       | `surface`                          |
| 타일      | outline    | 선택 시만            | 선택 시만           | 1 / offset −1 · `border`           |
| 패딩      | padding    | **20** (`p-5`)       | **16** (`p-4`)      | **24** (`p-6`)                     |
| 최소 높이 | min-height | **112** (`min-h-28`) | **96** (`min-h-24`) | 없음                               |
| 내부 간격 | gap        | 16 (`gap-4`)         | 16 (`gap-4`)        | **20** (`gap-5`) — `CardBody` 실측 |
| 값        | 타이포     | `metric-small`       | `metric-small`      | `metric-medium`                    |
| 라벨      | 타이포     | `body-medium`        | `body-medium`       | `body-medium`                      |
| 아이콘칩  | size       | —                    | —                   | 40                                 |

> **라벨 크기는 `compact` 와 다른 축이다.** 여백을 줄인다고 글자까지 줄지 않는다 —
> 아주 좁은 칸(상태 흐름)에서만 `denseLabel` 로 한 단 줄인다(`body-small`).
> 한때 `compact` 가 둘을 함께 처리해, 승격 과정에서 필터 대시 10화면의 라벨이
> 14 → 12 로 조용히 작아진 적이 있다.

### D3-5. 갈 곳이 있을 때만 버튼이 된다

**누를 수 없는 버튼은 키보드 사용자에게 빈 정거장이다** — 탭은 멈추는데 아무 일도 없다.

| 조건               | 렌더               | 이동 표식 |
| ------------------ | ------------------ | --------- |
| 이동할 화면이 있다 | `<button>` · `<a>` | ✅ 붙인다 |
| 값만 보여준다      | `<div>`            | ❌ 없다   |

표식을 이동 가능한 것에만 붙이면 **눌러보지 않고도** 어디로 이어지는지 구별된다.

> ⚠️ **`<button>` 에는 `w-full` 이 필수다.** 폼 컨트롤은 `display:flex` 를 줘도 폭이
> **shrink-to-fit** 이라 부모를 채우지 않는다. 그러면 우하단으로 밀어 둔 수치가
> 밀 공간이 없어 좌측에 붙는다 — 그리드 자식(`stretch`)인 타일은 멀쩡한데
> 흐름(§D5)만 어긋나 보이는 증상으로 나타난다.

## §D4. StatGrid — 건수 대시 = 필터

> 구현: `src/components/ui/StatGrid/`

목록 화면 상단의 "건수 카드"는 **지표가 아니라 필터다.** 누르면 표가 걸러진다.
`[실측]` 이 패턴이 **11곳**에 있고, 클래스 문자열이 **10개 파일에 그대로 복붙**돼 있다.

### D4-1. 선택은 테두리, hover 는 면 — 되돌리지 말 것

`design-core.md` **필수규칙 3** 을 여기에 옮겨 담는다. 이유가 길어서 잊히기 쉬운 규칙이다.

| 상태  | 처리                                                |
| ----- | --------------------------------------------------- |
| 기본  | `bg-surface-sub`                                    |
| hover | **면** — `bg-surface-slate-secondary`               |
| 선택  | **테두리** — `outline-action-primary` 2 / offset −2 |

> **왜 `action-primary-tonal` 을 쓰면 안 되는가** `[실측]`
> `action-primary-tonal` 은 `rgba(113,118,128,0.1)` 이라 흰 배경 위에서 `#f1f1f2` 가 된다.
> 바탕인 `surface-sub`(`#f8f9fb`)와 **2.4% 밖에 차이가 안 나면서**, hover 인
> `surface-slate-secondary`(`#e2e5e9`)보다는 **밝다.**
> 즉 **마우스만 올린 것이 골라 둔 것보다 진해져 선택 신호가 hover 에 진다.**
> 그래서 선택과 hover 가 **서로 다른 축**(선/면)을 쓰게 갈랐다.

### D4-2. 접근가능 이름

스크린리더는 `<button>` 안의 텍스트를 **이어 붙여 읽는다.** 라벨과 수치 사이에 공백이 없으면
"신규주문128건"이 된다. `aria-label` 로 읽을 문장을 직접 준다.

```
aria-label={`${label} ${count}${unit}`}   →  "신규 주문 128건"
aria-pressed={selected}                    →  선택 상태를 알린다
```

`role="group"` + `aria-label` 로 그리드 전체를 묶어 **"무엇을 고르는 곳인지"** 를 먼저 알린다.

### D4-3. Spec

| 항목      | 값                                                     |
| --------- | ------------------------------------------------------ |
| 열 수     | 항목 수에 맞춘다 — `[실측]` 실사용 2·3·4·5·6열         |
| 거터      | **12** (`gap-3`) — 필터 묶음은 한 덩어리로 읽혀야 한다 |
| 타일      | §D3 `variant="plain"` 과 동일                          |
| 값 타이포 | `metric-small`(24) — 필터는 지표보다 한 단 작다        |

> §D2-2 의 거터 24 는 **카드 사이** 값이고, 여기 12 는 **한 필터 묶음 안** 값이다.
> 묶음 안이 묶음 사이보다 좁아야 하나로 보인다.

## §D5. 상태 흐름 (퍼널)

주문·신청처럼 **단계를 따라 흐르는 것**은 목록으로 세우지 않고 **가로 체인**으로 잇는다.
그 순서가 곧 생애주기다.

```
결제완료  ›  배송준비  ›  배송중  ›  배송완료
  128         42          17         903
```

| 항목      | 값                                                                 |
| --------- | ------------------------------------------------------------------ |
| 컨테이너  | `role="list"` — 단계는 목록이다                                    |
| 단계      | §D3 `variant="plain"` · `compact`                                  |
| 연결자    | `ChevronRight` **24** · `strokeWidth 1.2` · `mx-2` · `aria-hidden` |
| 색        | **`chart-ordinal-1..4`** (§D7-3) — 순서가 색에 보여야 한다         |
| 최대 단계 | **4** — §D7-3 의 램프 상한과 같다                                  |

> **단계가 5개를 넘으면** 색으로 순서를 표현할 수 없다(§D7-3). 그때는 색을 빼고
> 위치(왼→오)에만 순서를 맡기거나, 단계를 묶어 4개로 줄인다.

> ⚠️ **단계에 중요도 등급을 매기지 않는다.** 한때 "처리 대기 합계"와 경보 배너를 세웠다가
> 되돌렸다 — 흐름은 **어디에 몇 개가 있는지**를 말하는 것이지 무엇이 급한지를 말하지 않는다.

## §D6. 수치 표현 규약

### D6-1. 수치 타이포 — 24종 밖의 별도 축

`[실측]` 지금까지 지표값과 페이지 제목이 **둘 다 `heading-2xlarge-bold`(24)** 였다.
화면에서 가장 큰 글자가 "이 페이지의 이름"인지 "오늘 매출"인지 구별되지 않았다.

| 프리셋          | px / line | weight | 쓰는 곳                                   |
| --------------- | --------- | ------ | ----------------------------------------- |
| `metric-large`  | 36 / 44   | 700    | 화면을 대표하는 단 하나의 수치            |
| `metric-medium` | 30 / 36   | 700    | KPI 행 (`variant="card"`)                 |
| `metric-small`  | 24 / 32   | 700    | 지표 타일 · 필터 대시 (`variant="plain"`) |

> **`heading-3xlarge~5xlarge` 와 크기가 같은데 왜 이름을 나누는가.**
> 역할이 다르기 때문이다. 나중에 밀도 축(§D10)이 생기면 **제목은 두고 수치만 줄일 수 있다.**
> 이름이 같으면 그렇게 못 한다.
> 그래서 `design-core.md` 의 _"확장 스케일은 대시보드에서 거의 쓰지 않는다"_ 는 문장은
> **그대로 유효하다** — 대시보드가 쓰는 것은 `heading` 이 아니라 `metric` 이다.

> **화면 전체에서 `metric-large` 는 하나뿐이다.** 둘이 되는 순간 어느 쪽도 대표가 아니다.

### D6-2. 등폭은 세로로 줄이 맞는 곳에만

`[실측]` Pretendard woff2 **4종 전부**(400/500/600/700)가 `tnum` 을 담고 있고,
Tailwind 에 `tabular-nums` 유틸리티도 있다. 그런데 `src/` 사용처가 **0회**다.

| 대상                    | 글자폭         | 이유                                                         |
| ----------------------- | -------------- | ------------------------------------------------------------ |
| 타일의 큰 수치 · 히어로 | **비례폭**     | 등폭은 모든 숫자에 `0` 의 폭을 준다 — `121` 이 헐거워 보인다 |
| **표의 수치 열**        | `tabular-nums` | 세로로 자릿수가 맞아야 대소가 보인다                         |
| **차트 축 눈금**        | `tabular-nums` | 같은 이유                                                    |
| 툴팁 안 수치            | `tabular-nums` | 값이 바뀌어도 폭이 안 흔들린다                               |

> ⚠️ `font-feature-settings` 를 쓰지 말 것 — 다른 feature 를 전부 리셋한다.
> **`font-variant-numeric: tabular-nums`**(= Tailwind `tabular-nums`)를 쓴다.

### D6-3. 큰 수 축약 — `Intl` compact 를 금액에 쓰지 않는다

`[실측]` Node 로 직접 실행한 `ko-KR` compact 결과:

| 입력       | 출력         | 문제                                       |
| ---------- | ------------ | ------------------------------------------ |
| 9,999      | **`1만`**    | **반올림이 자릿수 경계를 넘는다**          |
| 99,999     | **`10만`**   | 동일                                       |
| 12,345,678 | **`1235만`** | **4자리 + 쉼표 없음** → 타일 폭이 흔들린다 |
| 99,999,999 | **`1억`**    | 실제보다 크게 보인다                       |

CLDR 한국어 패턴이 `0000만`(10^7)로 **정수부 4자리를 강제**하기 때문이라
`maximumSignificantDigits` 로도 막히지 않는다. `compactDisplay: 'long'` 도 short 와 동일하다.

**처방** — 축약이 필요하면 `.data.ts` 에 만 단위 포맷터를 직접 둔다.

```
1,234만   ← 만 단위로 끊고 쉼표를 유지한다
```

> `[외부]` Polaris 축약 규칙: **"숫자 3자 + 소수 1자 + 문자 1자 이내"** — `12.5k` 는 되고
> `1234.5k` 는 안 된다. `1235만` 이 왜 문제인지에 대한 외부 근거다.
> `[외부]` 한글 맞춤법 **제44항**: 수는 **만 단위**로 띄어 쓴다(국립국어원).

**축약하지 않아도 되는 것은 축약하지 않는다.** `[외부]` Few 의 pitfall #3 — 대시보드는
필요 이상으로 정밀하면 안 되지만, **경계를 넘겨 거짓말하는 것보다는 긴 편이 낫다.**

### D6-4. 정렬 — 표는 좌측을 유지한다

`DESIGN.md` §7-2 의 **"수치도 좌측, 우측 정렬은 쓰지 않는다"** 를 **바꾸지 않는다.**

| 진영                                        | 규정                                  |
| ------------------------------------------- | ------------------------------------- |
| `[외부]` Polaris · Spectrum · Primer · KRDS | 양적 데이터 **우측**                  |
| **이 저장소**                               | 전부 **좌측** (배지 전용 열만 center) |

§7-2 는 회계 관행을 **알면서** 좌측을 택했고, 되돌릴 조건(`tabular-nums` 동반)까지 적어 두었다.
그러므로 이것은 무지가 아니라 판단이다. 다만 그 판단의 **정당한 절반**을 밝혀 둔다:

> `[외부]` **Spectrum 과 KRDS 가 독립적으로 같은 예외를 규정한다** —
> _"우편번호처럼 숫자로 보이지만 명목인 값은 좌측."_
> **날짜 · 전화번호 · 주문번호 · 사업자번호는 숫자처럼 보여도 명목 데이터라 좌측이 정석이다.**
> 이 저장소의 표에서 좌측인 열의 상당수가 여기에 해당한다.

**대시보드 타일의 수치는 표가 아니다.** 타일 안에서는 값을 **우하단**에 두어
라벨(좌상단)과 대각선으로 갈라 놓는다 — §D3-2.

### D6-5. 증감(delta) — 방향과 감정은 다른 축이다

| 축                | 뜻                 | 예                            |
| ----------------- | ------------------ | ----------------------------- |
| **방향** (`up`)   | 올랐나 내렸나      | 반품률 ↑ 도 `up = true` 다    |
| **감정** (`good`) | 그게 좋은가 나쁜가 | 반품률 ↑ 는 `good = false` 다 |

**두 축을 하나로 합치지 않는다.** 합치면 "반품이 늘어서 초록"이 된다.
`[외부]` Grafana `PercentChangeColorMode` · Datadog "Increases as better" 와 같은 설계다.

| 요소   | 규격                                                                                 |
| ------ | ------------------------------------------------------------------------------------ |
| 색     | `chart-delta-up` / `chart-delta-down` — **`StatTile` 이 `delta` prop 으로 강제한다** |
| 부호   | **항상 붙인다** — `+12.3%` / `−12.3%`                                                |
| 아이콘 | 방향 화살표 · `strokeWidth 1.2` · 12 또는 16                                         |
| 기준   | **비교 대상을 밝힌다** — "지난주 대비" (캡션 ⑦)                                      |

> **색만으로 전달하지 않는다** — 부호와 아이콘이 항상 함께 간다.
> `[외부]` Carbon Differential indicator: _"Color is optional … as long as the value has
> either a '+' or '-' in front of it, a chevron icon, or an arrow icon."_

**백분율은 `Intl` 을 그대로 써도 된다** `[실측]` —
`signDisplay:'exceptZero'` 가 `+12.3%` / `−12.3%` / `0%` 를 정확히 낸다. (§D6-3 의 문제는 compact 한정)

> **`%` 는 예외다 — 값에 붙여 쓴다.** `3.42%` 를 `3.42` + `%` 로 쪼개면 단위가 작아져
> 오히려 어색하다. 백분율은 관례상 한 덩어리로 읽힌다. `.data.ts` 에서는 `unit: ""` 로 두어
> **필드 구조는 다른 지표와 같게** 유지한다(타입이 갈라지지 않는다).

### D6-6. 통화

`[실측]` `Intl.NumberFormat('ko-KR',{style:'currency',currency:'KRW'})` → **`₩1,234,567`**
(기호 앞 · 공백 없음 · 소수 0자리). 원화는 CLDR 상 소수 자릿수가 **0** 으로 정의돼 있다.

이 저장소는 `.data.ts` 포맷터에서 **`12,000원`** 형태를 쓴다. 어느 쪽이든 **한 화면에서 섞지 않는다.**

> `[외부]` Polaris: **통화 음수는 부호를 통화기호 앞에** — `-$4.20`.
> 헤더에 단위를 넣었으면 **셀에서 단위를 반복하지 않는다.**

## §D7. 차트 색 레이어

`DESIGN.md` §28-1 은 **계열색(categorical) 하나**만 정했다. 색이 하는 일은 그것 말고도 있다.

### D7-1. 색의 네 가지 일

| 일         | 무엇을 말하나        | 토큰                           | 예                               |
| ---------- | -------------------- | ------------------------------ | -------------------------------- |
| **정체성** | 어느 계열인가        | `chart-series-1..5`            | 렌트 / 판매                      |
| **순서**   | 몇 번째 단계인가     | `chart-ordinal-1..4`           | 퍼널 · 등급 · 구간               |
| **극성**   | 기준선의 어느 쪽인가 | `chart-diverging-*`            | 목표 대비 · 증감                 |
| **상태**   | 좋은가 나쁜가        | `success`/`warning`/`critical` | 예약된 의미 — 계열로 쓰지 않는다 |

**하나의 색이 두 가지 일을 하지 않는다.** 상태색을 "4번 계열"로 쓰지 않고,
계열색을 "위험"으로 쓰지 않는다.

### D7-2. 정체성 — 계열색 5종 (기존, §28-1)

`[실측]` 검증 스크립트 실행 결과 — **라이트 모드 전 항목 통과.**

```
밝기 밴드 PASS · 채도 하한 PASS · 명암비 PASS
색각이상 분리도 PASS (최악 인접쌍 mango↔mint ΔE 10.3 deutan)
정상시각 분리도 PASS (최악 인접쌍 mint↔blue ΔE 16.1)
```

⚠️ **tritan(청황 색각이상) 분리도는 4.0** 으로 낮다. `DESIGN.md` §28-4 의 보조 수단
(범례 필수 · 직접 라벨 · 부호와 아이콘 병행)이 **장식이 아니라 판독의 전제**인 이유다.

### D7-3. 순서 — ordinal 램프 4단계 `[실측]`

단계·등급·구간처럼 **순서를 바꾸면 뜻이 달라지는 것**은 계열색이 아니라 한 색상의 명암 단계다.

| 토큰              | primitive | hex       |
| ----------------- | --------- | --------- |
| `chart-ordinal-1` | blue-500  | `#00b9ff` |
| `chart-ordinal-2` | blue-600  | `#0090d4` |
| `chart-ordinal-3` | blue-700  | `#0072ab` |
| `chart-ordinal-4` | blue-900  | `#065074` |

> **4단계가 상한이다.** 후보를 전수 검증한 결과 이 조합만 통과했다:
>
> | 후보                            | 결과                                                |
> | ------------------------------- | --------------------------------------------------- |
> | blue **500**/600/700/900        | ✅ 통과 (밝은 끝 명암비 2.18)                       |
> | blue 400 시작                   | ❌ `#2ccaff` 1.86 — 2:1 미달                        |
> | blue 300 시작                   | ❌ `#75dbff` 1.53                                   |
> | blue 200 시작                   | ❌ `#b6eaff` 1.26                                   |
> | blue 5단계(200/400/600/800/900) | ❌ 800↔900 밝기차 0.055 (< 0.06) — 단계가 안 보인다 |
> | slate 300/500/700/900           | ❌ `#bcc0c6` 1.78                                   |
>
> **크기(sequential) 표현도 같은 램프를 쓴다.** 값이 같은 토큰을 두 벌 두면
> 어느 쪽을 쓸지 매번 헷갈린다 — 이름은 하나, 용도는 문서가 가른다.

### D7-4. 극성 — diverging `[실측]`

기준선의 위/아래를 말할 때. **두 색은 따뜻함과 차가움으로 갈리고, 가운데는 무채색이다.**

| 토큰                      | primitive     | hex       |
| ------------------------- | ------------- | --------- |
| `chart-diverging-neg-3`   | coral-red-800 | `#a50f0f` |
| `chart-diverging-neg-2`   | coral-red-600 | `#ed1515` |
| `chart-diverging-neg-1`   | coral-red-400 | `#ff6464` |
| **`chart-diverging-mid`** | **slate-200** | `#dbdee3` |
| `chart-diverging-pos-1`   | blue-500      | `#00b9ff` |
| `chart-diverging-pos-2`   | blue-600      | `#0090d4` |
| `chart-diverging-pos-3`   | blue-900      | `#065074` |

양 팔 모두 램프 검증 통과 (밝은 끝 명암비 음 2.82 · 양 2.18).
**가운데는 반드시 무채색이다** — 색상이 들어가면 "아무것도 아님"으로 안 읽힌다.

### D7-5. 약화 — de-emphasis

| 토큰               | primitive | 쓰는 곳                                  |
| ------------------ | --------- | ---------------------------------------- |
| `chart-muted`      | slate-300 | "기타"로 접은 계열 · 강조 대비 배경 계열 |
| `chart-muted-fill` | slate-100 | 그 면                                    |

> **"강조"는 가장 저평가된 형태다.** 계열이 5개인데 말하려는 것이 하나라면,
> 색을 다섯 개 쓰지 말고 **하나만 계열색, 나머지를 `chart-muted`** 로 둔다.
> 6번째 계열이 필요할 때 색을 새로 만들지 않는 것과 같은 원리다(§28-1).

### D7-6. 차트 구조물 (furniture)

| 토큰         | primitive | 쓰는 곳             |
| ------------ | --------- | ------------------- |
| `chart-grid` | slate-100 | 격자 — **가로선만** |
| `chart-axis` | slate-200 | 축 선               |
| `chart-tick` | slate-500 | 눈금 텍스트         |

지금까지 `--color-divide` 를 빌려 쓰고 있었다. **차트 구조물은 표의 구분선과 다른 것**이라
따로 이름을 준다 — 나중에 격자만 더 연하게 하고 싶을 때 표를 건드리지 않아도 된다.

### D7-7. 증감 — 상태색과 분리한다

| 토큰                  | primitive      | hex       | 흰 배경 대비 `[실측]` |
| --------------------- | -------------- | --------- | --------------------- |
| `chart-delta-up`      | neon-green-800 | `#086c0c` | **6.64** ✅           |
| `chart-delta-down`    | coral-red-700  | `#c80d0d` | **5.97** ✅           |
| `chart-delta-neutral` | slate-500      | `#717680` | 4.56                  |

**왜 `text-success` / `text-critical` 을 그대로 쓰지 않는가** `[실측]`:

| 현행 토큰                       | 흰 배경 대비 | 텍스트 4.5:1 | 마크 3:1 |
| ------------------------------- | ------------ | ------------ | -------- |
| `text-success` (neon-green-600) | **2.76**     | ❌           | ❌       |
| `text-critical` (coral-red-600) | **4.45**     | ❌ (아슬)    | ✅       |

증감 수치는 **작은 글자**라 텍스트 대비 기준을 받는데 현행 상태색은 둘 다 미달이다.

> **두 번째 이유 — 문화 의존을 격리한다.** `[외부]` 한국 증권 관례는 **상승=빨강 · 하락=파랑**으로
> 세계에서 독특하다(미국·유럽은 상승=초록, 일본·중국은 하락=초록). 커머스 대시보드에도
> 적용되는지에 대한 공개 근거는 **없다.**
> 그래서 초기값은 **현행 방향(상승=초록)** 으로 두되, 토큰을 분리해 **`dashboard.json` 두 줄만
> 고치면 뒤집히게** 해 두었다.
> `[외부]` 제3의 선택지도 있다 — Polaris Viz 는 `TREND_NEGATIVE` 를 빨강이 아니라 **회색**으로 둔다.

### D7-8. ⚠️ 상태색이 계열색을 사칭한다 `[실측]`

계열 5색 + 상태 3색을 **전체 대조**한 결과:

```
❌ critical #ed1515 ↔ series-5 raspberry #fe5868   ΔE 10.2 (기준 15 미달)
❌ success  #00b505 ↔ warning  #e28100             ΔE  4.0 (deutan)
```

**차트에 5번 계열이 나오는 화면에서는 같은 영역에 위험 태그를 놓지 않는다.**
정상 시각으로도 구분이 어렵다. 계열이 5개까지 가는 차트라면 계열 5를 쓰지 말고
`chart-muted` 로 접거나 차트를 나눈다.

### D7-9. 차트는 흰 면 위에 놓는다 `[실측]`

계열색의 명암비는 **배경에 따라 달라진다.**

| 계열                | `surface` #ffffff | `surface-sub` #f8f9fb |
| ------------------- | ----------------- | --------------------- |
| 1 blue-600          | 3.54 ✅           | 3.36 ✅               |
| 2 mint-700          | 3.62 ✅           | 3.44 ✅               |
| 3 mango-800         | 4.98 ✅           | 4.72 ✅               |
| 4 grape-500         | 4.35 ✅           | 4.13 ✅               |
| **5 raspberry-500** | **3.08** ✅       | **2.93** ❌           |

**계열 5는 흰 면 위에서만 3:1 을 통과한다.** 그러므로 —

> **차트는 `surface`(흰 카드) 위에 놓는다. `surface-sub` 위에 놓지 않는다.**

인접 계열끼리의 대비는 1.02~1.61 에 불과하다. `DESIGN.md` §28-2 의
**"도넛 조각 사이 `surface` stroke 2"** 가 정확히 이 문제의 해법이다 —
색끼리 맞닿는 곳은 **흰 틈**이 갈라 준다.

### D7-10. 색 참조 방법 (함정 — §28-1 재확인)

```
✅  CHART_SERIES_COLORS[i]            // 배열 상수
❌  `var(--color-chart-series-${i})`  // Tailwind 스캔 실패 → 배포 CSS 에서 변수 소멸
```

**새로 추가한 ordinal · diverging 토큰도 같다.** 인덱스로 조립하지 말고 배열 상수를 만든다.

## §D8. 데이터 상태

대시보드는 **타일 단위로 실패한다.** 한 칸이 안 왔다고 화면 전체를 에러로 덮지 않는다.

### D8-1. 로딩 — 시간이 처방을 정한다

| 구간    | 처방                                             | 근거                  |
| ------- | ------------------------------------------------ | --------------------- |
| < 0.1s  | **아무것도 표시하지 않는다**                     | `[외부]` Nielsen 1993 |
| < 1s    | 표시자가 오히려 방해 — 넣지 않는다               | `[외부]` NN/g         |
| 1 ~ 10s | **스켈레톤**(구조가 있는 곳) / 스피너(단일 모듈) | `[외부]` NN/g         |
| > 10s   | **진행률 표시**                                  | `[외부]` NN/g         |

> `[외부]` Carbon: _"use skeleton states instead of spinners."_
> `[외부]` Cloudscape: _"a spinner provides no structural context and can increase
> perceived loading time and layout shift."_ — 표·타일처럼 **레이아웃이 정해진 곳은 스켈레톤**이다.

**스켈레톤을 쓰지 않는 곳** `[외부]` Carbon — 토스트 · 오버플로 메뉴 · 드롭다운 항목 · 모달 · 로더.
**고정 텍스트는 스켈레톤으로 만들지 않는다** `[외부]` Polaris — "주문 목록" 같은 제목은
어차피 안 바뀌므로 **실제 텍스트로 렌더**하고 변하는 것만 가린다.

**갱신(refetch)은 스켈레톤으로 되돌리지 않는다.** 이전 렌더를 **낮은 불투명도로 유지**한다 —
레이아웃이 튀지 않고, 방금 본 값과 비교할 수 있다.

### D8-2. 빈 상태 ≠ 에러

> `[외부]` Cloudscape: _"never use empty states for errors."_

| 상황             | 처리                                                       |
| ---------------- | ---------------------------------------------------------- |
| 데이터가 없다    | `EmptyState` — **다음 행동**을 제시                        |
| 필터 결과가 없다 | 제목 "검색 결과 없음" · 버튼은 **항상 "필터 초기화"**      |
| 실패했다         | **에러 표시 + 재시도** — `EmptyState` 를 재사용하지 않는다 |

> `[외부]` NN/g: 제목은 **긍정문으로** — _"데이터를 추가해 시작하세요"_ 가
> _"데이터가 없습니다"_ 보다 낫다. 그리고 **로딩이 끝나기 전에 "없음"을 보여주지 않는다** —
> 신뢰가 깨진다.

### D8-3. 부분 실패 — 실패한 칸만 바꾼다

> `[외부]` Cloudscape: _"Use error boundaries when a specific part of a page fails but the
> rest is still usable (e.g., charts, drawers, split panels)."_

| 범위      | 처리                                                       |
| --------- | ---------------------------------------------------------- |
| 타일 하나 | **그 컨테이너 내용만** 에러로 교체 + 재시도. 나머지는 산다 |
| 화면 전체 | 메인 콘텐츠를 알림으로 대체                                |

### D8-4. 신선도 (stale)

자동 갱신되는 화면은 **언제 것인지**를 말해야 한다.

| 항목          | 규격                                             |
| ------------- | ------------------------------------------------ |
| 갱신 시각     | "N분 전 업데이트" — 갱신 성공 후 표시            |
| 지연          | 10초를 넘기면 **대기 표시자**                    |
| 실패          | **경고 표시자** + 이유 + 재시도                  |
| 새로고침 위치 | **헤더 액션에만** — 화면 곳곳에 흩어 두지 않는다 |

### D8-5. 지금 없는 것 `[실측]`

| 항목                          | 상태                            |
| ----------------------------- | ------------------------------- |
| `Skeleton` 컴포넌트           | **없음** (`Spinner` 만 있다)    |
| `DataTableShell` 의 `loading` | **없음** (`empty` prop 만 있다) |
| `DataTableShell` 의 `error`   | **없음**                        |

이 절은 **규격을 먼저 세워 둔 것**이다. 구현은 별도 작업이다(§D13).

## §D9. 접근성

### D9-1. SVG 는 스크린리더에 전달되지 않는다

| 항목        | 규격                                                       |
| ----------- | ---------------------------------------------------------- |
| 차트 프레임 | `role="img"` + `aria-label` — `ChartFrame` 이 이미 한다    |
| 대체 수단   | **값에 도달할 다른 경로**를 반드시 둔다 (표 · 퍼센트 목록) |
| 범례        | 계열이 **2개 이상이면 항상** 노출                          |

> `[외부]` **WCAG 1.4.11 면제 조항** — 파이 조각은 _"if values of the pie chart slices were
> also presented in a conforming manner"_ 면 대비 요구가 면제된다.
> `DESIGN.md` §28-4 의 _"도넛은 퍼센트 목록을 함께 둔다"_ 가 정확히 이 조항과 맞는다 —
> **이미 정석이다.**

### D9-2. 색만으로 전달하지 않는다

> `[외부]` Cloudscape: _"**There is no such thing as a true 'color-blind safe' palette.**"_

| 대상       | 색 외에 반드시 함께 가는 것      |
| ---------- | -------------------------------- |
| 계열       | 범례 + (가능하면) 직접 라벨      |
| 증감       | **부호 + 화살표 아이콘** (§D6-5) |
| 상태       | **아이콘 + 텍스트 라벨**         |
| 단계(순서) | **위치**(왼→오) — 색은 보조      |

> `[외부]` Carbon Status indicator: 4요소(Symbol/Shape/Color/Type) 중 **최소 3개** —
> _"even in grayscale, users should still be able to differentiate statuses."_

### D9-3. 텍스트에 계열색을 입히지 않는다

값 · 라벨 · 범례 글자는 `text-*` 토큰을 쓴다. **정체성은 옆에 놓인 색 마크가 담당한다.**
계열색 중 밝은 것은 글자로 쓰면 배경 대비가 무너진다(§D7-9).

### D9-4. 라이브 리전 — 지금 빠져 있는 것 `[실측]`

`aria-live` / `role="status"` 가 **`Toast` 와 `SelectionBar` 에만** 있다.
**필터를 적용해 결과 건수가 바뀌어도 스크린리더에 전달되지 않는다** — WCAG **4.1.3** 미충족.

| 알려야 할 것     | 예                        |
| ---------------- | ------------------------- |
| 필터 결과 건수   | "128건이 검색되었습니다"  |
| 자동 갱신 완료   | "방금 업데이트되었습니다" |
| 비동기 로딩 완료 | —                         |

> `[외부]` Primer: **750ms 이전에 도착한 내용은 공지하지 않는다** — 과한 공지가 오히려 방해다.

### D9-5. 툴팁은 값에 이르는 **유일한** 경로가 아니다

호버로만 읽을 수 있는 값은 키보드·터치 사용자에게 없는 값이다.
툴팁은 **보강**이고, 값은 직접 라벨이나 표에도 있어야 한다.

`[외부]` WCAG 1.4.13 — 호버로 뜬 내용은 **Dismissible / Hoverable / Persistent** 여야 한다.
차트 라이브러리 기본 툴팁은 대개 Hoverable(툴팁 위로 마우스를 옮겨도 유지)을 만족하지 못한다.

## §D10. 밀도 — 지금은 이름만 정한다

어드민은 같은 화면을 하루 8시간 본다. 정보량을 사용자가 고를 수 있어야 한다는 것이
`[외부]` Spectrum · Cloudscape · SLDS 가 공통으로 도달한 결론이다.

**지금 구현하지 않는다.** 다만 **무엇이 변하고 무엇이 안 변하는지**만 정해 둔다 —
나중에 `[data-density="compact"]` 한 줄로 전환할 수 있게.

| 변하는 것       | regular | compact | 근거               |
| --------------- | ------- | ------- | ------------------ |
| 테이블 행 높이  | 48      | 40      | `--size-table-row` |
| 카드 padding    | 24      | 16      |                    |
| `CardBody` gap  | 20      | 16      |                    |
| 타일 min-height | 112     | 96      |

| **변하지 않는 것**       | 이유                                                                   |
| ------------------------ | ---------------------------------------------------------------------- |
| 타이포 24종 + `metric-*` | `[외부]` Cloudscape 565개 토큰 중 변하는 24개에 **폰트는 하나도 없다** |
| 컨트롤 높이 48/40/32/28  | 밀도로 바꾸면 터치 목표가 무너진다                                     |
| 색 전부                  | 밀도는 공간의 문제다                                                   |

> `[외부]` Spectrum 은 `size`(S/M/L/XL) × `density`(compact/regular/spacious) **2축**으로
> 12조합을 토큰으로 공표한다. 그중 `compact` 는 **컨트롤 높이 토큰을 그대로 재사용**한다 —
> 우리 48/40/32/28 이 Spectrum medium scale(48/40/32/24)과 거의 같으므로,
> 밀도를 넣을 때 **새 값을 만들 필요가 없다.**

## §D11. 한국어 조판

### D11-1. 줄바꿈 — `keep-all` `[실측 0회]`

> `[외부]` W3C CSS Text 3, `word-break: normal`: _"Korean … **allows breaks between any two
> consecutive Hangul/Hanja**."_

**기본값에서 한글은 음절 아무 데서나 끊긴다.** 좁은 타일 안에서 "신규 주"/"문" 으로 갈린다.

```css
word-break: keep-all;
overflow-wrap: break-word; /* 긴 단어가 넘칠 때의 탈출구 */
```

> `[외부]` MDN: `keep-all` 은 _"Non-CJK text behavior is the same as for `normal`"_ —
> **영문·숫자에 부작용이 없어 전역 적용이 안전하다.** 대한민국 정부 디자인시스템(KRDS)의
> 전역 리셋이 정확히 이 조합을 쓴다.
> `[실측]` 원본 아임웹은 `keep-all` 을 5회 쓰고 `.tw-break-keep` 유틸리티도 갖고 있다.
> 이 저장소 `src/` 는 **0회.** Tailwind 에 `break-keep` 유틸리티는 이미 있다.

**적용 대상**: 타일 라벨 · 빈 상태 문구 · 차트 축 라벨 — **줄이 좁고 문장이 짧은 곳.**

### D11-2. 수 읽기

`[외부]` 한글 맞춤법 **제44항** — 수는 **만 단위**로 끊어 읽는다("일, 만, 억, 조").
3자리 쉼표(`1,234,567`)는 표기 관행이고, **읽기 단위는 4자리**다.
축약할 때 만 단위로 끊는 것(§D6-3)은 이 때문이다.

| **`word-break: keep-all`**     | §D11-1 이 타일 라벨에 규정했으나 `src/` 사용 0회                                                                                                                                                       |
| **기존 10화면 일괄 교정**      | §D2-4 의 거터 불일치, §D4 의 복붙 제거는 별도 작업이다                                                                                                                                                 |

```
증감     chart-delta-up  chart-delta-down  chart-delta-neutral
진행     progress-warning        ← ProgressBar 전용. mustard-700 (DESIGN.md §26-1)
```

> `progress-warning` 이 왜 따로 있나 — `border-warning`(mustard-500)·`icon-warning`(mustard-600)은
> 트랙(`#e2e5e9`) 위 대비가 각각 **1.51 · 2.25** 로 비텍스트 3:1 에 미달한다. mustard-700 은 **3.66** 이다.
> `text-warning-hover` 가 같은 색이지만 **hover 토큰을 정적 색으로 빌려 쓰면 hover 를 재매핑하는 날
> 조용히 깨지므로** 전용 토큰을 둔다.

> ⚠️ `StatTile` 은 받은 DOM props 를 루트로 **그대로 흘려보낸다.** `Tooltip` 이
> `cloneElement` 로 주입하는 핸들러·`ref`·`aria-describedby` 가 DOM 까지 닿아야
> 툴팁이 열리기 때문이다. 이 spread 를 지우면 **에러 없이 툴팁만 죽는다.**

> ⚠️ **토큰이 있다고 배포 CSS 에 나오는 것은 아니다.** Tailwind v4 의 `@theme` 는
> **소스에서 실제로 발견된 것만** 출력한다. 아래 19개 중 `chart-delta-*` 3개만
> `StatTile` 이 쓰고 있고, 나머지(구조물·순서·극성·약화)는 쓰는 화면이 생길 때 나온다.
> `metric-large` 도 같다.

> 원시 색은 **하나도 추가하지 않았다** — 전부 기존 `blue` · `coral-red` · `slate` · `neon-green`
> 램프를 참조한다. 브랜드를 갈아끼우면 이 토큰들도 함께 따라간다.
