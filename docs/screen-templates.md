# screen-templates.md — 화면 템플릿 카탈로그

> **Stage 5(화면 생성)가 읽는 정본.** 어떤 화면을 어느 템플릿으로 만들지, 무엇을 갈아끼우고
> 무엇을 그대로 둘지를 여기서 정한다.
> 실물: `src/pages/*.tsx`(뼈대) + `src/pages/*.data.ts`(도메인) · 규격: `docs/DESIGN.md`

---

## 0. 전제 — 페이지는 "예제"가 아니라 "템플릿"이다

각 페이지는 두 파일로 갈려 있다.

| 파일        | 담는 것                            | 서비스가 바뀌면    |
| ----------- | ---------------------------------- | ------------------ |
| `*.tsx`     | 레이아웃 · 상호작용 · 범용 유틸    | **거의 그대로**    |
| `*.data.ts` | 타입 · 데이터 · 라벨 · 단위 포맷터 | **전부 새로 쓴다** |

두 파일 **상단의 구조 계약 주석**이 이 문서의 세부 사항을 담고 있다.
템플릿을 고치면 그 주석도 함께 고칠 것 — **생성기는 주석을 읽는다.**

> ⚠️ **주석과 실물 코드가 어긋나면 실물 코드가 사실이다.** 주석은 설명이지 계약이 아니다.
> 그리고 계약은 **이름이 아니라 역할과 모양**이므로, 이름이 갈려 있어도 판단이 막히지 않는다(§3 머리말).

> ⚠️ 단위 포맷터(`won` 등)가 여러 `.data.ts` 에 중복되는 것은 **의도된 것**이다.
> 단위는 도메인이라(원 · kg · 시간 · 건) 공용화하면 서비스 교체 시 뼈대를 고쳐야 한다.

## 1. 템플릿 4종

| 유형       | 실물              | 하는 일                                                                       | 교체 방식               |
| ---------- | ----------------- | ----------------------------------------------------------------------------- | ----------------------- |
| **목록형** | `OrderListPage`   | 집합을 표로 보여주고 필터·검색·기간으로 좁힌 뒤, 행을 열어 상세를 보거나 액션 | **데이터만**            |
| **상세형** | `OrderDetailPage` | 한 건을 여러 관점(요약·명세·금액·부가정보)으로 나눠 제시                      | **데이터만**            |
| **통계형** | `DashboardPage`   | 핵심 지표 + 추이·구성비·순위를 차트와 표로                                    | **데이터만**            |
| **폼형**   | `ProductFormPage` | 섹션으로 나눈 입력 폼. 검증·조건부 필드 포함                                  | ⚠️ **필드를 다시 쓴다** |

### 왜 폼형만 다른가

`.data.ts` 로 빠진 것이 **선택지 배열 2개와 포맷터 1개**뿐이다. 나머지는 뺄 수 없다.

1. 필드마다 컨트롤이 다르다 — Input · Select · SegmentedControl · Textarea · RadioGroup · DatePicker · Switch · Checkbox **8종**. 데이터로 빼려면 "종류 → 컴포넌트" 디스패처, 즉 **폼 DSL** 을 만드는 일이 된다
2. 필드 상태 8개의 타입이 제각각 (`string` · `boolean` · `DateRange | undefined`)
3. 검증이 **폼 단위**다 — 할인가 오류는 두 필드의 상호 비교, 이름 오류는 `touched` 와 결합
4. 조건부 노출이 필드 존재 여부와 도움말 문구 **두 군데**에 걸친다
5. 컨트롤별 부속 prop(`rightIcon` · `inputMode` · `minRows` · `labelAction`)이 그 필드 전용
6. `FormField` 의 `group` 여부가 컨트롤 종류에 종속

**→ 폼형이 재사용하는 것은 데이터가 아니라 레이아웃 규칙이다.** 그것만으로도 값어치가 크다(§3-4).

## 2. 유형 판정 — `keyScreens[]` 에서 무엇을 보는가

`01-service-brief.json` 의 각 화면에서 `name` · `purpose` · `sections` · `components` 를 읽고 아래 신호로 고른다.

| 신호 (한 개라도 강하게 걸리면)                                                                        | 유형       |
| ----------------------------------------------------------------------------------------------------- | ---------- |
| 목록 · 리스트 · 관리 · 조회 · 검색 · 필터 · 페이징 · 테이블 / `components` 에 `Table`·`Pagination`    | **목록형** |
| 등록 · 수정 · 편집 · 작성 · 설정 · 신청 / `components` 에 `Input`·`Select`·`Textarea`·`Checkbox` 다수 | **폼형**   |
| 상세 · 정보 · 내역 · 명세 · 프로필 / 단일 레코드를 가리키는 `purpose`                                 | **상세형** |
| 대시보드 · 현황 · 통계 · 지표 · 분석 · 리포트 / `components` 에 `Chart`                               | **통계형** |

### 판정 규칙

- **한 화면의 유형 판정이 갈릴 때 목록형을 우선한다.** 이것은 **한 화면**이 목록 신호와 상세 신호에 동시에 걸릴 때의 규칙이지, 화면 개수를 줄이라는 뜻이 아니다.
- **기획서가 목록과 상세를 별도 화면으로 분리했으면(= `keyScreens[]` 의 서로 다른 항목) 둘 다 만든다.** 이때는 유형 판정이 갈린 것이 아니라 화면이 둘인 것이다. 목록형 하나로 합치지 않는다.
- **어느 것에도 안 걸리면 만들지 말고 물어본다.** 억지로 배정하면 뼈대가 화면을 왜곡한다.
- `sections` 에 모바일 어휘(`Dock Bar` · `Status Bar` · `메인 배너`)가 있어도 **데스크톱 관리자 화면으로 변환**한다 — 이 저장소는 데스크톱 전용이다(`CLAUDE.md`). 기획서가 모바일 앱이면 그 사실을 보고하고 진행 여부를 물을 것.

> ⚠️ **"목록형이 상세를 이미 품고 있다"는 말은 사실이 아니다.**
> 목록형의 미리보기(`Modal`)는 `InfoList` **4항목짜리**이고, 뼈대(`OrderListPage.tsx`)가 스스로
> "사이드시트는 빠른 미리보기다 — 전체 정보는 상세 페이지에서 본다"고 적고 **`전체 상세 보기` 버튼**으로
> 상세 화면(`order-detail`)에 내보낸다.
> 명세 표·금액 내역(§30-5)·부가 정보 카드는 미리보기에 **들어가지 않는다** — 상세형에만 있다.
> 상세가 필요한 화면을 목록형의 미리보기로 대신하면 **정보가 통째로 빠진다.**

### 4종으로 안 되는 화면

로그인 · 온보딩 · 랜딩 · 결제 · 채팅 등은 템플릿이 없다.
**없는 것을 있는 척하지 말고**, 계획서(`05-screen-plan.json`)에 `template: null` + `reason` 으로 남기고
사용자에게 알린다. 나중에 템플릿이 늘면 그때 채운다.

## 3. 템플릿별 계약

생성한 `.data.ts` 가 아래를 어기면 **화면이 런타임에 조용히 깨진다.** 생성 후 반드시 확인할 것.

> ⚠️ **계약은 이름이 아니라 "역할과 모양"을 고정한다.**
> 아래 표의 `Order` · `ORDERS` · `won` 같은 식별자는 **이커머스 템플릿의 실물 이름일 뿐** 계약이 아니다.
> 계약인 것은 **역할**(어느 자리에 꽂히는가)과 **모양**(필수 필드 · 개수 · 형식)이다.
>
> **생성한 화면은 도메인 이름을 쓰는 것이 옳다** — 병원 예약이면 `Reservation` · `RESERVATIONS` · `minutes`.
> 템플릿 이름을 그대로 복사하면 병원 화면에 `Order` 타입이 남는다.
> 이름을 바꾸면 짝이 되는 뼈대(`*.tsx`)의 import 와 참조도 **같이 바꾼다** — 이름을 잇는 것은 타입 검사가 잡아준다.
>
> 그래서 실물 `.data.ts` 상단 주석의 이름과 실제 export 이름이 달라 보일 수 있다
> (`OrderListPage.data.ts` 주석 표는 `Row`·`ROWS`·`formatMain`, 실제 export 는 `Order`·`ORDERS`·`won`).
> **둘 중 어느 이름도 계약이 아니다** — 역할과 모양만 맞추면 된다.

### 3-1. 목록형 (`OrderListPage`)

#### 상단 건수 대시 = 필터 (`StatGrid`)

목록 화면 맨 위의 "건수 카드"는 **지표가 아니라 필터다.** 누르면 아래 표가 걸러진다.
직접 `<button>` 을 조립하지 말 것 — 그 복붙이 **10개 화면에 퍼졌다가** 걷어낸 이력이 있다.

```tsx
<StatGrid
  items={dash.map((item) => ({
    value: item.value, // 필터 값 (key 겸용)
    label: item.label,
    count: num(item.count), // ⚠️ 이미 포맷된 문자열. 단위는 넣지 않는다
    unit: SOME_UNIT, // "건" "명" "개사" …
    tip: item.tip, // 설명이 필요한 항목만
  }))}
  selected={filter}
  onSelect={selectFilter}
  ariaLabel="회원 상태" // 무엇을 고르는 묶음인지
  columns={5} // 2~6, 항목 수에 맞춘다
/>
```

⚠️ **상태 축의 컨트롤은 이것 하나뿐이다.** 툴바에 `SegmentedControl` 을 함께 두지 마라 —
**한 축에 컨트롤이 둘**이 되어 어느 쪽이 참인지 읽는 사람이 판단하게 된다.
세그먼트는 기간·단위처럼 **건수가 없는 축**에 쓴다.

`StatGrid` 가 대신 책임지는 것 — `role="group"` · 접근가능 이름 조립(`라벨 값단위`) ·
**선택은 테두리 / hover 는 면**(`design-core.md` 필수규칙 3) · 툴팁 분기.
규격: `DESIGN-dashboard.md` §D4.

| 역할 (템플릿 실물 이름)   | 뜻                    | 계약                                                                                     |
| ------------------------- | --------------------- | ---------------------------------------------------------------------------------------- |
| 행 타입 (`Order`)         | 표 한 행              | **`id`**(고유키) · **`date`**(`YYYY-MM-DD HH:mm` — 기간 필터가 파싱) 필수                |
| 상태 맵 (`STATUS_META`)   | 상태 → 라벨·`TagTone` | 키가 행 타입의 `status` 와 **정확히 일치** · 상태가 색보다 많을 때는 아래 "상태 색 배정" |
| 행 배열 (`ORDERS`)        | 샘플 데이터           | 5건 내외 (페이징이 보이게)                                                               |
| 요약 카드 (`STATS`)       | 상단 요약 카드        | **3장** (grid-cols-3) · `icon` 은 lucide 컴포넌트 참조 · **`up`·`good` 필수**(§3-5)      |
| 필터 (`FILTERS`)          | 툴바 세그먼트         | **`[0].value === "all"`** (뼈대가 필터 해제로 취급)                                      |
| 수치 포맷 (`won`)         | 주요 수치 포맷        | 천 단위 구분자 **쉼표 필수** (아래 ⚠️)                                                   |
| 페이지 크기 (`PAGE_SIZE`) | 페이지당 행 수        | 샘플이 적으면 3~5                                                                        |

> ⚠️ **수치 포맷터의 구분자를 바꾸면 검증이 조용히 깨진다.** 폼형 뼈대가 `Number(x.replace(/,/g, ""))` 로
> 되돌리기 때문이다. 공백·마침표를 쓰지 말 것.

#### 행을 눌러 여는 미리보기 (`sideSheetItems`)

> ⚠️ **실물은 `Modal`(가운데)이다.** 한때 `SideSheet`(우측 패널)였고 계약 이름(`sideSheetItems`)에
> 그 흔적이 남아 있지만, **가운데 모달이 사용자 결정**이다(커밋 `0c7f9ed`). 이름은 하류 계약이
> 걸려 있어 그대로 두었다 — **이름이 아니라 실물을 따른다.**
> 기획서가 "우측에서 본다"처럼 **패널을 명시**하면 그때만 `SideSheet` 를 쓰고 계획서에 근거를 남긴다.

`InfoList` 4항목 내외의 **빠른 미리보기**다. 전체 정보는 푸터의 "전체 상세 보기"가 가리키는 상세형 화면에서 본다.

- **제목은 "○○ 미리보기"** — 상세 화면과 이름이 겹치지 않게. `"○○ 상세"` 로 두면 **같은 이름의 화면이 둘**이 되어,
  사용자는 어느 쪽을 열었는지, 다음 생성자는 어느 화면 얘기인지 알 수 없다
  (템플릿 실물도 `OrderListPage` 의 시트가 `"주문 상세"` 였는데 `OrderDetailPage` 의 제목과 겹쳐 `"주문 미리보기"` 로 고쳤다)
- 상세형을 만들지 않는 도메인이라도 미리보기로 부른다 — 시트에 전체 정보를 밀어 넣지 말라는 신호가 제목에 남는다
- 항목이 4개를 크게 넘으면 시트가 아니라 상세형이 필요하다는 뜻이다

#### 상태 색 배정 — 상태가 `TagTone` 보다 많을 때

`TagTone` 은 `default` · `success` · `warning` · `critical` · `custom` 5종이고, 이 중 상태를 뜻하는 색은 **4종**이다(`Tag.tsx`).
상태가 4개를 넘는 도메인은 흔하다 — 예약은 확정·미확정·완료·노쇼·취소 **5개**가 자연스럽다.

**상태 개수를 억지로 줄이지 말 것.** 도메인을 왜곡하는 것보다 색이 겹치는 편이 낫다. 아래 순서로 배정한다.

1. **`warning` 은 "지금 주의를 요하는 상태"가 독점한다** (미확정 · 입금대기 — 누가 무언가를 해야 끝난다)
2. **`critical` 은 "지금 주의를 요하는 상태" + "비정상 종료"가 나눠 쓴다.**
   취소·반려·실패·노쇼는 **이미 끝났지만 정상적으로 끝나지 않은 것**이라, 정상 종료(완료)와 색으로 구별할 값어치가 있다.
   목록을 훑을 때 "잘못된 건이 몇 개인가"는 라벨을 읽지 않고도 보여야 한다
3. **정상 종료는 `default`.** 완료·배송완료처럼 **제대로 끝난 일**은 더 볼 것이 없어 눈에 띌 이유가 없다
4. 진행 중이고 정상인 상태에 `success` (확정 · 결제완료)
5. 그래도 부족하면 **`tone="custom"` + `--tag-bg-color`/`--tag-color`** 로 넓힌다. 주입하는 값은 **semantic 토큰(`var(--color-*)`)만** — 하드코딩 금지(`Tag.tsx` 의 `TagCustomStyle` 주석)

> `Tag` 는 라벨 텍스트를 항상 함께 보여주므로 **색이 겹쳐도 상태는 글자로 구별된다.**
> 색은 "주의가 필요한가"를 훑어보게 하는 보조 신호이지 상태의 유일한 식별자가 아니다.

> **이 규칙은 템플릿 실물과 일치한다** — `OrderListPage.data.ts` 의 `STATUS_META` 는
> 결제완료 `success` · 배송준비중 `default` · 입금대기 `warning` · **취소 `critical`** 이다.
> 초안에서는 "종료 상태는 전부 `default`"라고 적었다가, 재리허설에서 **템플릿이 그 규칙의 반례**임이
> 드러나 **규칙 쪽을 고쳤다.** 취소를 회색으로 묻으면 목록에서 문제 건이 보이지 않는다.

#### 분류 배지 — 상태가 아닌 것에 색을 줄 때

위 규칙은 **상태**에 대한 것이다. 표에는 상태가 아닌 배지도 자주 있다 — 유형(렌트/판매),
판매자(본사/셀러), 계층(대/중/소분류), 자격(인증 여부), 강조(고정).
**여기에 상태색(`success`·`warning`·`critical`)을 쓰면 안 된다.** "렌트는 좋은 상태"처럼
읽혀 없는 신호가 생긴다. 그다음이 갈리는 지점인데, 기준은 **대등한가**이다.

| 종류                  | 예                                   | 배정                      |
| --------------------- | ------------------------------------ | ------------------------- |
| **대등한 분류**       | 렌트↔판매 · 본사↔셀러 · 대↔중↔소분류 | **전부 `default`**        |
| **플래그(있음/없음)** | 위생인증 · 공지 고정 · KC 인증       | `custom` + highlight 허용 |

**대등한 분류에서 한쪽만 칠하지 않는다.** 렌트에만 highlight 를 주면 렌트가 특별한 건으로
보이는데, 실제로는 대등한 두 값이다. 게다가 **같은 행에 상태 `Tag` 가 이미 색을 쓰고 있어**,
분류까지 칠하면 한 행에서 색이 두 축을 다투게 된다. 구별은 글자가 한다
(`Tag` 는 라벨을 항상 함께 보여준다).

플래그는 다르다 — "있음"만 배지가 뜨고 "없음"은 아예 없거나 회색이라 비대칭이 **의도**다.
이때만 `tone="custom"` + `--tag-bg-color`/`--tag-color` 에 semantic 토큰을 주입한다.

> **이 조항이 없어서 실제로 갈렸다** (BabyCube 28화면 생성). 한 배치는 렌트를 highlight 로,
> 다른 배치는 `default` 로 칠했고 **양쪽 다 "분류에 상태색 금지"라는 같은 근거**를 댔다.
> 위 항목 5(`custom` 으로 넓히기)를 분류에 끌어다 쓴 것이 원인인데, **항목 5는 "상태가
> 4색보다 많을 때"의 규칙이지 분류를 다루지 않는다.** 이 표가 그 공백을 메운다.

### 3-2. 상세형 (`OrderDetailPage`)

| 역할 (템플릿 실물 이름) | 계약                                                        |
| ----------------------- | ----------------------------------------------------------- |
| 레코드 객체 (`ORDER`)   | ⚠️ **자유롭지 않다** — 뼈대가 경로째 참조한다. 아래 표 참고 |
| 파생 합계               | 뼈대가 아니라 데이터에서 계산 (`itemsTotal` · `total`)      |
| 수치 포맷 (`won`)       | 목록형과 동일                                               |

- 카드는 **1열 스택**. 2열 grid 를 만들지 않는다(§30-4)
- 금액 내역은 `InfoList` 가 **아니라** `justify-between` 목록이다(§30-5) — 숫자를 세로로 비교해야 한다
- 라벨이 80px 을 넘으면 `labelWidth` 로 덮되, **기본값일 때는 주지 않는다**(배타 분기)

#### 레코드 객체의 실제 계약 — 뼈대가 경로째 참조한다

"중첩 구조 자유"가 아니다. `OrderDetailPage.tsx` 는 아래 경로를 **직접** 읽으므로,
이름이나 깊이를 바꾸면 **뼈대도 함께 고쳐야 한다.** 도메인에 맞게 바꾸는 것은 당연하지만
**바꾼 만큼 뼈대를 손봐야 한다는 사실**을 알고 시작할 것.

| 경로                                    | 뼈대에서 쓰이는 곳             | 성격                                       |
| --------------------------------------- | ------------------------------ | ------------------------------------------ |
| `status: { label, tone }`               | PageHeader `badges` · InfoItem | **계약** — 목록형 `STATUS_META` 와 같은 급 |
| `items[]: { name, option, qty, price }` | 명세 표 4열                    | 열 구성을 바꾸면 표 JSX 도 바꾼다          |
| `payment.*` · `buyer.*` · `shipping.*`  | 각 카드의 InfoList             | 카드 구성에 맞춰 자유롭게 재편 가능        |
| `shippingFee` · `discount`              | 금액 내역 + 합계 계산          | 항목이 늘면 `amountBreakdown` 도 늘린다    |

> `status.tone` 은 `TagTone` 이어야 한다(§3-1 "상태 색 배정" 참고).

### 3-3. 통계형 (`DashboardPage`)

#### KPI 카드는 `StatTile variant="card"` 다

`Card` + `CardBody` 로 직접 짜지 말 것. 증감 색·아이콘·부호를 `StatTile` 이 책임진다.

```tsx
<StatTile
  variant="card"
  label={label}
  value={value} // ⚠️ "1,284" — 단위를 합치지 않는다
  unit={unit} // "건" ( `%` 는 예외: value 에 붙이고 unit="" )
  icon={<Icon size={20} strokeWidth={1.2} aria-hidden />}
  caption={caption} // 비교 기준 — 카드마다 따로
  delta={{ text: delta, up, good }}
/>
```

**값과 단위를 한 문자열로 합치면 단위까지 30px 이 되어 자릿수가 안 읽힌다**(§D3-3).
`delta` 의 `up`(방향, 아이콘)과 `good`(감정, 색)은 **다른 축**이다 — §3-5 참조.
색은 `chart-delta-*` 를 쓴다(상태색은 틴트 배경 위에서 명암비가 4.5:1에 미달한다).
규격: `DESIGN-dashboard.md` §D3 · §D6-5.

| 역할 (템플릿 실물 이름)         | 계약                                                                                                                         |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| KPI 카드 (`KPIS`)               | **4장** (grid-cols-4) · **`up`·`good` 필수**(§3-5) · **`caption`(비교 기준) 필수**(아래 ⚠️) · `icon` 은 lucide 컴포넌트 참조 |
| 차트 데이터 (`REVENUE` 등)      | 값 단위를 미리 맞출 것 — 축과 툴팁이 **같은 포맷터**를 공유한다                                                              |
| 계열 (`*_SERIES`)               | `ChartSeries[]` — 계열이 2개 이상이면 **범례 필수** · `key` 가 데이터 객체의 속성 이름과 정확히 일치                         |
| 포맷터 (`manwon` 등)            | 단위별로 하나씩 · `number` 와 `string` 을 **둘 다** 받는다(툴팁 값이 문자열로 들어온다)                                      |
| 기간 세그먼트 (`PERIODS`)       | ⚠️ **뼈대의 `useState` 초기값과 하드 커플링** — 아래                                                                         |
| 도넛 중앙 합계 (`channelTotal`) | 구성비 데이터의 파생 집계. 뼈대는 퍼센트만 계산한다                                                                          |
| 순위 표 (`TOP_PRODUCTS`)        | 표 열 구성을 바꾸면 표 JSX 도 바꾼다                                                                                         |

> ⚠️ **`PERIODS` 를 새로 쓰면 뼈대의 초기값도 같이 고쳐야 한다.**
> `DashboardPage.tsx` 가 `useState("12m")` 로 시작하는데, 이 `"12m"` 이 `PERIODS[].value` 중
> 하나가 아니면 **SegmentedControl 에 활성 항목이 없는 채로 렌더된다.**
> 타입으로는 잡히지 않는다 — 문자열이라서. 값을 바꾸면 **양쪽을 같이 본다.**

> ⚠️ **`caption`(비교 기준)을 카드 4장이 공유하게 만들지 말 것.**
> 이커머스 템플릿은 4장이 우연히 같은 기간과 비교해 `"지난 기간 대비"` 로 겹치지만,
> **비교 기준은 지표마다 다르다** — 병원이면 오늘 예약은 당일, 노쇼율은 최근 30일,
> 평균 대기는 최근 7일 평균이다. 한 문구로 묶으면 **노쇼율 4.2%(최근 30일)가 오늘 건수
> (2/38 = 5.3%)와 비교되는 것처럼 읽혀 숫자가 서로 모순되는 화면**이 된다.
> 그래서 뼈대에 박지 않고 `KPIS[].caption` 으로 카드마다 데이터가 들고 온다 —
> 기준이 정말 같은 도메인이라도 **같은 문자열을 4번 적는다.** 생략하면 다음 사람이 또 뼈대에 박는다.

- 차트 색은 **`CHART_SERIES_COLORS[i]` 배열 상수**로만. `` `var(--color-chart-series-${i})` `` 조립 금지 — Tailwind 스캔이 놓쳐 배포 CSS 에서 변수가 사라진다(§28-1)
- 타입을 새로 달지 말 것 — 차트 배열은 `ChartDatum`(`Record<string, string | number>`)에 **암묵적 index signature 로 대입**되므로 인터페이스를 붙이면 대입이 깨진다

#### 5개 제한이 걸리는 곳 / 안 걸리는 곳

계열색은 5종이고 `seriesColor(i)` 가 `Math.min(i, 4)` 로 **5번째 색에 고정**한다(순환하지 않는다).
다만 그 `i` 에 **무엇이 들어가는지가 차트마다 다르다** — `Chart.tsx` 실물:

| 차트                        | 색 인덱스 `i` 의 정체    | 실물 코드                                              | 5개 제한 대상   |
| --------------------------- | ------------------------ | ------------------------------------------------------ | --------------- |
| `LineChart` (라인·에어리어) | **계열 인덱스**          | `series.map((s, i) => <Line stroke={seriesColor(i)}>)` | 계열 수         |
| `BarChart` (막대)           | **계열 인덱스**          | `series.map((s, i) => <Bar fill={seriesColor(i)}>)`    | 계열 수         |
| `DonutChart` (도넛)         | **데이터 포인트 인덱스** | `data.map((d, i) => <Cell fill={seriesColor(i)}>)`     | **데이터 개수** |

**→ 데이터 개수로 색이 갈리는 것은 도넛뿐이다.** 단일 계열 막대 차트는 막대가 3개든 12개든
전부 `seriesColor(0)` **한 색**이라 막대 개수와 색이 아무 관계가 없다.

- **도넛 데이터**: **5개 이하.** 6번째 조각부터 5번째 색에 눌려 앞 조각과 구별되지 않는다 → "기타"로 접는다
- **계열(`*_SERIES`)**: 차트 종류와 무관하게 **5개 이하.** 넘으면 계열을 접거나 차트를 나눈다
- **막대·라인의 데이터 포인트 개수**: **색 때문에 줄일 이유가 없다. 도메인이 요구하는 구간을 그대로 쓴다.**
  (시간대별 예약 09~18시 8구간을 색 때문에 5구간으로 접지 말 것 — 도메인이 왜곡된다.
  축 라벨이 겹쳐 읽기 어려운 것은 **가독성 문제**로 따로 판단한다)

### 3-4. 폼형 (`ProductFormPage`) — 재사용하는 것은 레이아웃 규칙

데이터가 아니라 **아래 6가지를 상속**한다. 필드는 기획서를 보고 새로 쓴다.

1. **카드 = 섹션** — 논리 묶음 하나가 카드 하나
2. **간격을 페이지가 지정하지 않는다** — `AppShell` gap-6(카드 24) · `CardBody` gap-5(필드 20) · `FormField` gap-1.5(라벨↔입력 6)
3. **`FormField` 의 `group`** — `RadioGroup`·`SegmentedControl` 은 루트가 `<div role="radiogroup">` 이라 `<label for>` 로 이름이 안 붙는다. **`group` 없으면 접근가능 이름이 아예 없다**
4. **에러가 도움말을 대체한다** — 같은 자리에서 교체(§29-5)
5. **컨트롤 병치는 `flex` + `flex-1 min-w-0`** — 2열 grid 금지(§29-4). 단 `Input` 의 `min-w-60` 때문에 **2칸에 최소 488px** 필요
6. **`Switch`·`Checkbox`·`Radio` 는 자체 `label` prop 사용** — `FormField` 로 감싸지 않는다

### 3-5. 증감 지표 — `up`(방향)과 `good`(감정)은 **다른 축**이다

목록형의 `STATS`(§3-1)와 통계형의 `KPIS`(§3-3)가 공유하는 계약이다. **두 필드를 모두 넣는다.**

| 필드   | 뜻                   | 무엇을 정하는가                      |
| ------ | -------------------- | ------------------------------------ |
| `up`   | 값이 **올랐는가**    | 화살표 `TrendingUp` / `TrendingDown` |
| `good` | 그 변화가 **좋은가** | Tag tone `success` / `critical`      |

```ts
// .data.ts — 방향과 감정을 따로 적는다
{ label: "노쇼율", value: "4.2%", delta: "-1.2%p", up: false, good: true, icon: … }
```

```tsx
// 뼈대 — 아이콘은 방향, 색은 감정
<Tag tone={good ? "success" : "critical"} size="small">
  {up ? (
    <TrendingUp size={12} strokeWidth={1.2} aria-hidden />
  ) : (
    <TrendingDown size={12} strokeWidth={1.2} aria-hidden />
  )}
  {delta}
</Tag>
```

- ⚠️ **`up` 하나로 화살표와 색을 겸용하지 말 것.** 이커머스(매출·주문·방문자)는 지표가 전부 "오르면 좋다"라 **우연히** 일치할 뿐이다. 도메인이 바뀌면 어긋난다 — 병원 예약에서 노쇼율 `-1.2%p` 는 **내려갔고(`up: false`) 좋은 것(`good: true`)** 인데, 겸용하면 빨강으로 그려진다
- **"오르면 좋다"가 성립하는 도메인에서도 `good` 을 생략하지 않는다.** 생략하면 다음 사람이 또 겸용한다
- **요약 카드에 `tone` 을 하드코딩하지 않는다** — 색은 언제나 데이터(`good`)가 정한다
- `delta` 문자열에는 **부호를 직접 넣는다**(`+18.2%` · `-1.2%p`) — 증감을 색만으로 전달하지 않기 위해서다
