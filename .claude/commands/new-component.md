디자인 시스템에 없는 UI 부품을 **설계 → 구현** 2단계로 만듭니다.
있는 것으로 되면 만들지 않습니다.

## 팀 구성 — 전문성을 나눈다

| 단계     | 담당                       | 정하는 것                                                 | 안 하는 것             |
| -------- | -------------------------- | --------------------------------------------------------- | ---------------------- |
| 1 설계   | `@agent-ux-designer`       | 필요성 판정 · anatomy · 상태 · 상호작용 · 접근성 · 콘텐츠 | 코드를 쓰지 않는다     |
| 2 구현   | `@agent-component-builder` | 4파일 + 배럴 + 검증                                       | 설계를 바꾸지 않는다   |
| 3 게이트 | `@agent-design-qa`         | 8항목 검사                                                | 파일을 수정하지 않는다 |

> **왜 갈랐나.** 구현하면서 설계하면 "코드가 쉬운 쪽"으로 설계가 끌려간다 —
> 그때 제일 먼저 희생되는 것이 접근성과 상태 처리다.

## 절차

1. **`@agent-ux-designer`** 에 인자($ARGUMENTS)를 그대로 전달한다
   (예: `/new-component 목표 대비 진행률을 보여주는 게이지`).
   → 기존 37종으로 되면 **여기서 끝난다.** 조합 방법을 답으로 받는다.
   → 아니면 **설계 명세**를 받는다. **여기서 정지 · 사용자 승인.**
2. 승인되면 **`@agent-component-builder`** 에 그 명세를 **본문째** 넘긴다.
   → 구현 계획 보고 · 정지 · 승인 → 4파일 생성 + 배럴 등록 + 검증.
3. **`@agent-design-qa`** 8항목 게이트.
4. 문서 반영이 필요하면 마지막에 안내한다(`DESIGN.md` §26 표에 한 줄 등).

## 규칙

- **명세 없이 2단계로 건너뛰지 않는다.** 급해 보여도 설계가 먼저다.
- 구현자가 명세와 충돌을 발견하면 **고쳐서 만들지 말고 보고**한다 — 명세가 정본이다.
