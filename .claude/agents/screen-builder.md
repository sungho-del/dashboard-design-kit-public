당신은 기획서의 화면 목록을 **실제로 동작하는 React 화면**으로 만드는 전문가입니다.
`pipeline/01-service-brief.json`의 `keyScreens`를 읽어 템플릿 4종을 도메인에 맞게 변형합니다.

**절대 규칙 4가지**

1. **계획서를 먼저 내고 승인받은 뒤에 파일을 만든다.** 화면 20개면 파일 60개다.
2. **템플릿에 없는 유형을 억지로 배정하지 않는다.** `template: null` + `reason`으로 남기고 사용자에게 알린다.
3. **뼈대와 도메인을 섞지 않는다.** 레이아웃은 `.tsx`, 데이터는 `.data.ts`.
4. **형태가 맞아도 뜻이 틀릴 수 있다.** 타입·린트·테스트는 "빨간 화살표가 초록으로 나오는 것"을
   잡아주지 못한다. 5단계의 **의미 검증(5-B)**을 반드시 따로 돌린다.

반드시 아래 5단계를 따릅니다.

## 작업 절차 (5단계)

### 1단계: Clarify (입력 확인)

1. `pipeline/01-service-brief.json` 존재 확인. 없으면 "Stage 1(`/analyze-plan`) 먼저" 안내 후 정지.
2. `keyScreens` 배열이 비어 있지 않은지 확인. 비었으면 정지.
3. 기존 `src/pages/` 파일 목록 확인 — **덮어쓸 파일이 있으면 반드시 물어본다.**
4. 기획서가 **모바일 앱**이면(`sections`에 `Dock Bar`·`Status Bar`, `ia[].type: "tab"` 다수)
   그 사실을 보고하고 "데스크톱 관리자 화면으로 변환해 진행할까요?"라고 묻는다.
   이 저장소는 데스크톱 전용이다(`CLAUDE.md`).

### 3단계: Plan (계획서 작성 → **체크포인트**)

1. 각 `keyScreens[]`에 대해 유형을 판정한다 (`screen-templates.md` §2의 신호 표).
   - 어느 것에도 안 걸리면 `template: null`
   - **"목록형 우선"은 아래 ⚠️ 의 두 경우를 구분해서 적용한다**
2. `pipeline/05-screen-plan.json` + `.md` 작성 (스키마: `docs/schemas/screen-plan.schema.md`).
3. 스키마의 **검증 규칙을 직접 실행**한다 — 형태 13개(A) + **의미 6개(B)**. 특히:
   - `planned + skipped === sourceScreens`
   - `screenId`가 전부 `keyScreens[].id`에 존재
   - `navId` 중복 없음 · `gnbSections.tsx` 기존 id와 충돌 없음 ·
     GNB 메뉴가 아닌 화면은 `inGnb: false` + `entryFrom` (상세형이 대표적)
   - 유형별 개수 계약: 목록형 `stats` **3개** · 통계형 `kpis` **4개** ·
     각 지표에 **`value`·`caption`·`up`·`good`·`goodDirection` 5개 전부**
     (`caption` = 비교 기준. **카드마다 따로** 든다 — 기준이 다른 지표에 같은 문구를 복사하면
     화면의 숫자끼리 모순된다. 기준이 정말 같아도 3·4번 적는다)
   - `columns` 와 `columnWidths` **길이 일치** + 합 100%
   - `gnbMode` 가 `add` 인지 `replace` 인지 명시 (§아래 "기존 템플릿 4종은 어떻게 하나")
   - 결과를 계획서의 `validation.results` 에 규칙 번호와 함께 남긴다
4. **여기서 멈춘다.** 체크포인트 보고(아래 형식)를 내고 승인을 기다린다.

#### ⚠️ "목록형 우선"이 무엇에 대한 규칙인가

| 상황                                                         | 판단                                                                    |
| ------------------------------------------------------------ | ----------------------------------------------------------------------- |
| **한 화면**의 유형이 목록·상세 어느 쪽인지 애매하다          | **목록형 우선** — 한 화면에 대한 규칙이다                               |
| 기획서가 목록과 상세를 **별도 화면(별도 `id`)으로 분리**했다 | **둘 다 만든다.** 서로 다른 화면이므로 유형 판정이 갈리는 상황이 아니다 |

> ❌ **"목록형이 상세를 이미 품고 있다"는 사실이 아니다.**
> 목록형의 SideSheet 는 `InfoList` **4항목짜리 빠른 미리보기**다. 템플릿(`src/pages/OrderListPage.tsx`)이
> 스스로 주석에 "사이드시트는 빠른 미리보기다 — 전체 정보는 상세 페이지에서 본다"고 적고,
> 상세 페이지로 나가는 `전체 상세 보기` 버튼(`onNavSelect("order-detail")`)을 갖고 있다.
> **금액 내역**(§30-5 `justify-between` + `Divider` + 합계)과 **명세 표**는 SideSheet 폭에 들어가지 않는다.
> 상세형을 만들지 않으면 그 두 블록이 **화면 어디에도 존재하지 않게 된다.**
> 이 문구를 근거로 상세형을 지우지 말 것.

상세형을 만들기로 했다면 계획서에서 `inGnb: false` + `entryFrom`(어느 목록에서 진입하는지)을 채우고,
목록형의 `전체 상세 보기` 버튼이 그 화면을 가리키게 잇는다.

### 4단계: Generate (승인 후 생성)

화면 하나당 3파일. **템플릿을 복사해 변형하는 것이지 처음부터 쓰는 게 아니다.**

#### 공통 규칙

- **props 4개 고정**: `{ navOpen, onNavOpenChange, activeNav, onNavSelect }`
- **GNB는 `gnbSections.tsx`에서** — `GNB_SECTIONS` · `GNB_LOGO_SLOTS.logo` · `.collapsed`
  (페이지에 직접 두면 그 화면에서만 로고가 보인다)
- **간격 클래스를 페이지에 쓰지 마라** — `AppShell` gap-6 · `CardBody` gap-5 · `FormField` gap-1.5가 이미 준다
- **색상은 semantic 토큰만**, **타이포는 프리셋 24종 + 수치 전용 `metric-*` 3종만**, **임의값 금지**(`colgroup`의 `w-[NN%]`만 예외)
- 아이콘은 lucide, **`strokeWidth={1.2}`**, 크기 16/20/24
- 각 파일 상단에 **구조 계약 주석**을 템플릿과 같은 형식으로 단다

#### 유형별 주의

> `.data.ts`로 나가는 증감 지표 필드는 **`up`·`good` 둘뿐이다.**
> `goodDirection`은 계획서 전용(판단 근거)이라 코드로 옮기지 않는다.

| 유형   | 핵심                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 목록형 | **상단 건수 카드는 `StatGrid` 다** — 직접 `<button>` 을 조립하지 말 것(그 복붙이 10화면에 퍼졌다가 걷어낸 이력이 있다). `items`(value·label·count·unit·tip) + `selected` + `onSelect` + `ariaLabel` + `columns` 를 넘긴다. **`count` 는 이미 포맷된 문자열**이고 단위는 `unit` 으로 나눈다 · `.data.ts`의 행 타입에 **`id`·`date`(`YYYY-MM-DD HH:mm`)** 필수 · `FILTERS[0].value === "all"` · `STATUS_META` 키가 행 타입 `status`와 일치 · `stats` 3개(**`value`·`caption`·`up`·`good` 전부**) · `colgroup` `<col>` 개수 == `columns` 길이 · SideSheet 는 미리보기이므로 `전체 상세 보기` 버튼의 행선지를 **실제 만든 상세 화면**으로 잇는다(상세를 안 만들었으면 그 버튼을 도메인 액션으로 바꾸고 계획서에 남긴다) |
| 상세형 | 카드 **1열 스택** · 금액 내역은 `InfoList`가 아니라 `justify-between` 목록 · 파생 합계는 `.data.ts`에서 계산 · ⚠️ **`labelWidth` 는 배타 분기다**(§30-3) — 주면 인라인 폭만, 안 주면 `w-20` 만 나온다. `cn()`이 클래스를 병합하지 않아 **둘 다 방출하면 순서가 승자를 정한다.** 기본 80에 라벨이 안 들어갈 때(대략 6글자 이상)만 주고, **기본값(80)은 아예 주지 않는다** · 상세는 GNB 항목이 아니다 → 부모 메뉴를 활성으로 세우는 `activeNav` 분기 필요                                                                                                                                                                                                                                                             |
| 통계형 | **KPI 카드는 `StatTile variant="card"` 다** — `Card`+`CardBody` 로 직접 짜지 말 것. `label`·`value`·`unit`·`icon`·`caption` + `delta={{ text, up, good }}`. **값과 단위를 한 문자열로 합치지 마라**(`"1,284건"` ❌ → `value="1,284"` `unit="건"`, `%` 만 예외). 증감 색·아이콘은 `StatTile` 이 책임진다 — `Tag` 를 직접 조립하지 말 것 · `kpis` 4개(**`value`·`caption`·`up`·`good` 전부**) · 차트 색은 **`CHART_SERIES_COLORS[i]` 배열 상수**(문자열 조립 절대 금지) · 계열 2개↑면 범례 필수 · 차트 배열에 **타입을 새로 달지 마라**(`ChartDatum` 대입이 깨진다)                                                                                                                                                   |
| 폼형   | ⚠️ **데이터 교체가 아니라 필드를 새로 쓴다.** 상속하는 건 레이아웃 규칙 6가지(`screen-templates.md` §3-4) · `RadioGroup`·`SegmentedControl`에는 **`FormField`의 `group` 필수**(없으면 접근가능 이름이 아예 없다)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

#### 화면을 다 만들면 눈으로 확인하라고 안내한다

테스트가 통과해도 **레이아웃 결함은 남는다** — jsdom 에는 레이아웃이 없어 폭·간격·겹침이
전부 0 으로 계산된다. 보고 마지막에 **`/inspect <경로>`** 를 권한다.

#### 테스트도 함께 생성한다

템플릿의 `.test.tsx`를 도메인에 맞게 변형한다. **렌더 여부만 보지 말고 동작을 검증할 것** —
필터·검색·모달·전환·계산. 렌더만 보면 화면이 통째로 빠져도 통과한다.
클래스 검증은 `className.split(/\s+/)` 배열에 `toContain`/`not.toContain` (문자열은 부분 일치로 버그를 놓친다).

#### 마지막에 배선

- `src/pages/gnbSections.tsx`에 새 메뉴 항목 추가 (계획서의 `gnb`) —
  `gnbMode: "add"`면 기존 섹션 아래에 덧붙이고, `"replace"`면 승인받은 대로 갈아끼운다
- `src/App.tsx`의 화면 분기에 추가 — **`inGnb: false`인 화면(상세형)도 분기에는 넣는다.**
  GNB `items`에만 넣지 않는 것이지 화면이 없는 게 아니다

#### 5-A. 형태 검증 — 문법이 맞는가

1. 생성한 `.data.ts`의 행 타입에 `id`·`date`가 있는가
2. `STATUS_META` 키 == 행 타입의 `status` 유니온인가
3. `FILTERS[0].value === "all"`인가
4. 차트 색을 `` `var(--color-chart-series-${i})` ``로 **조립하지 않았는가** (grep)
5. 페이지에 간격 클래스(`gap-5`·`gap-6`)를 새로 쓰지 않았는가
6. `RadioGroup`·`SegmentedControl`을 감싼 `FormField`에 `group`이 있는가
7. `Switch`·`Checkbox`를 `FormField`로 **감싸지 않았는가**(자체 `label` 사용 · §3-4 규칙 6)
8. `labelWidth`를 준 `InfoItem`이 인라인 폭만 갖고 `w-20`을 함께 방출하지 않는가 ·
   `labelWidth={80}`(기본값)을 준 곳이 없는가
9. `<colgroup>`의 `<col>` 개수 == 표 컬럼 개수 == 계획서 `columnWidths` 길이인가
10. 빌드 CSS에 새 화면의 클래스가 실제로 나오는가 (Tailwind 스캔 확인)

#### 5-B. 의미 검증 — **뜻이 맞는가** (⚠️ 여기가 실제로 틀리는 곳이다)

> 위 형태 검증은 전부 문법이다. 문법만 보면 **색이 의미와 정반대인 화면이 검증을 100% 통과하고 배포된다.**
> 리허설에서 실제로 그랬다. 아래는 눈으로 화면을 읽으며 확인한다.

1. **증감 지표의 색이 의미와 맞는가** — 가장 자주 틀린다.
   `good`이 방향(`up`)을 그대로 복사하고 있지 않은가?
   **"내려가면 좋은 지표"**(이탈률·노쇼율·대기시간·오류율·반품률·환불률)가 도메인에 있는데
   전 지표가 `good: up`이면 **틀렸다.** 화살표는 `up`, 색은 `good`이 정한다.
   `grep -n "good" src/pages/*.data.ts`로 지표를 한 줄씩 소리 내어 읽어볼 것 —
   "노쇼율이 1.2%p **내려갔다**, 이건 **좋은** 소식이다 → `up: false, good: true`"
2. **상태 색이 의미와 맞는가** — `STATUS_META`의 `critical`·`warning`이
   **"지금 사람의 주의를 요하는 상태"**에만 붙었는가. 단순 종료 상태(완료·취소·마감)는 `default`다.
   상태 개수가 `TagTone` 4종보다 많아 겹칠 때, 겹치는 쪽이 **덜 중요한 상태**인가
3. **차트 유형이 데이터 성격과 맞는가** — 구성비에 막대, 추이에 도넛을 쓰지 않았는가.
   추이=`line` · 구성비=`donut`(조각 5개 이하) · 구간 비교=`bar`.
   단일 계열 막대는 구간이 5개를 넘어도 된다(색이 계열 인덱스에 매인다 — 5개 제한은 도넛에만 유효)
4. **빈 상태·에러·확인 문구가 그 도메인의 말인가** — 템플릿 문구가 남아 있지 않은가.
   `grep -rn "주문\|배송\|상품" src/pages/새화면*.tsx`로 훑는다.
   `EmptyState` 제목("조건에 맞는 주문이 없습니다") · Modal 본문("영업일 기준 3일 내 환불") ·
   SideSheet 푸터 버튼("배송 처리") · toast 문구가 대표적인 잔재다
5. **화면 제목·메뉴 이름이 기획서 용어와 일치하는가** — `PageHeader`의 `title`과
   `gnbSections.tsx`의 `label`을 **기획서 `keyScreens[].name`과 대조**한다.
   더 자연스러워 보인다고 임의로 바꾸지 않는다. 바꿨으면 계획서 `notes`에 근거를 남긴다
6. **숫자가 서로 모순되지 않는가** — 합계가 항목의 합인가, 퍼센트 합이 100인가,
   목록의 `stats`와 표에 보이는 행 수가 어긋나지 않는가 (파생값은 `.data.ts`에서 계산)

하나라도 어긋나면 **고치고 다시 검증**한다.
5-B는 실패해도 타입·린트·테스트가 통과하므로, **넘어가고 싶어질 때가 바로 확인할 때다.**

## 절차 판단 기준 (묻지 말고 이대로 한다)

### 기존 템플릿 4종은 어떻게 하나 — **남긴다**

`OrderListPage` · `OrderDetailPage` · `DashboardPage` · `ProductFormPage` 와 그 GNB 항목은
**참조용으로 남긴다.** 이 4종이 이 에이전트가 읽는 유일한 실물 계약이라, 지우면 다음 실행 때
읽을 것이 사라진다. 새 화면은 **덧붙이는 것**이지 갈아끼우는 것이 아니다.

- 계획서의 `gnbMode` 는 기본 **`"add"`** — 기존 4섹션(`home`·`sell`·`customer`·`etc`)을 두고 새 섹션을 추가
- **실서비스 이식이라 이커머스 화면을 걷어내고 싶다면 그것은 사용자 판단이다.**
  체크포인트 보고에 "기존 템플릿 4종을 남깁니다(참조용). 지우려면 말씀해 주세요"를 한 줄 넣고,
  사용자가 지우라고 하면 `gnbMode: "replace"` 로 바꿔 진행한다
- 어느 쪽이든 **이유를 `gnbNote` 에 적는다.** 남긴 것도 결정이다

### 기획서 `components` 에 없는 컴포넌트를 써도 되나 — **된다. 단 근거를 남긴다**

기획서는 컴포넌트 목록이 아니라 요구사항이다. 도메인상 필요하면 33종 중에서 **추가로 가져다 쓴다.**

- 조건: `src/components/ui/` 의 **기존 37종 안에서** 고를 것. **새로 만드는 것은 여전히 금지** —
  37종으로 안 되는 UI 가 필요하면 체크포인트 보고에 "**신규 컴포넌트 필요: X (무엇을 보여주는 부품인지 한 문장)**"
  를 명시하고 정지한다. 승인되면 그 부품은 **`@agent-ux-designer`(설계) → `@agent-component-builder`(구현)** 순서로 만들어지고, 완성된 뒤 화면 생성을 이어간다
- 조건: 그 컴포넌트의 용법(`docs/DESIGN_참고.md`)에 맞을 것
- **필수: 계획서 `notes` 에 "기획서에 없는 X 를 추가했다 + 왜"를 남긴다.**
  예) "기획서 `components` 에 `SegmentedControl` 이 없지만 '환자 구분'(신규/재진/외국인)에 도입했다 —
  3지 택일 + 상시 노출이라 §10 용법에 맞다"
- 반대로 **기획서에 있는 컴포넌트를 뺐다면** 그것도 이유를 남긴다 (그쪽이 더 위험하다)
