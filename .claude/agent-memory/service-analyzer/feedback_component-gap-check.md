`keyScreens[].components` 를 쓸 때 "이 UI 가 있는가"는 **세 곳을 순서대로** 확인하고 판정한다.
이름만 보고 있다/없다를 단정하지 않는다.

**Why:** 이름이 그럴듯한 컴포넌트가 실제로는 요구를 못 채우는 경우가 있고, 반대로
"없다"고 결론 낸 것이 이미 설계 지침으로는 존재하는 경우가 있다. 둘 다 하류 Stage 의
판단 근거를 망가뜨린다 — 전자는 없는 기능을 있다고 넘기고, 후자는 이미 있는 규격을
버리고 새로 발명하게 만든다.

**How to apply:**

1. **배럴이 정본** — `src/components/ui/index.ts` 의 export 이름과 대조한다.
   눈으로 세지 말고 스크립트로 파싱해 대조할 것(정규식을 셸 `node -e` 에 인라인하면
   백슬래시가 깨져 **전부 unknown 으로 나오는 오탐**이 난다. 스크립트 파일로 빼서 실행한다).
2. **"없다"고 쓰기 전에 `docs/DESIGN.md` §26** 을 본다 — "원본에 없는 컴포넌트 — 설계 지침"
   표에 미구현 컴포넌트의 규격이 미리 적혀 있다(ProgressBar·Skeleton·Breadcrumb 등).
   여기 있으면 "새로 만들어야 함"이 아니라 **"지침을 구현으로 승격"** 이라고 적어야 한다.
   덧붙여 그 지침이 기획서 요구를 **다 채우는지**까지 확인한다(예: 임계값에 따른 색 분기는
   §26 ProgressBar 지침에 없다).
3. **유사 컴포넌트는 구현을 열어 제약을 확인** — 특히 `Chart` 의 `BarChart` 는 이름과 달리
   **세로 전용**이다(`radius:[4,4,0,0]` 로 위만 둥글고 바닥이 기준선에 붙으며,
   축·그리드·툴팁을 동반하는 `ChartFrame` 래퍼). 표 셀 안 인라인 가로 막대나
   "라벨+수치+막대 한 줄" 목록형 표현으로 **쓸 수 없다.**

판정 결과는 `meta.gaps` 와 해당 화면의 `notes` **양쪽에** 적는다 — gaps 는 사용자 질문용,
notes 는 Stage 5 가 화면을 만들 때 읽는 자리라 역할이 다르다.
