파이프라인 단계를 리허설로 돌릴 때는 **막히거나 어색했던 지점, 계약이 안 맞았던 부분,
문서에서 부족하다고 느낀 것을 감추지 말고 그대로 보고**한다. 성공 요약보다 실패 목록이 우선이다.

**Why:** 사용자가 Stage 5 리허설을 지시하며 명시했다 — "막히거나 어색한 지점을 감추지 말고
그대로 보고하라. **잘 된 것보다 안 된 것이 이 리허설의 산출물이다.**" 리허설의 목적이
절차가 굴러가는지 확인하는 것이지 결과물을 뽑는 게 아니기 때문이다.

**How to apply:**

- 리허설·검증·드라이런 성격의 작업이면 최종 보고에 "관찰/문제" 섹션을 별도로 둔다.
  절차 중 애매했던 판정, 계약이 억지로 맞은 부분, 스키마·문서에 자리가 없던 정보를 모두 적는다.
- 문서와 코드가 어긋난 것 같으면 **추측하지 말고 코드를 읽어 확인한 뒤** 어느 쪽이 맞는지 단정한다
  (CLAUDE.md의 "추측을 사실처럼 말하지 말 것"과 같은 취지).
- 판단이 갈리는 지점은 결론만 쓰지 말고 **어느 규칙을 왜 적용/미적용했는지** 근거를 남긴다.
- 발견한 결함을 임의로 고치지 않는다 — 보고하고 지시를 기다린다.
